# 全平台登录注册模块设计评估报告

## 一、现有设计合理性分析

### ✅ 设计亮点

**1. SSO 多端统一认证架构**
`oauth_clients` 表预注册了 6 个客户端（web/h5/miniprogram/admin/ios/android），`user_sessions` 表通过 `client_id + platform` 联合索引支持多端会话隔离，Token TTL 按平台差异化配置（管理端 3600s vs 移动端 86400s），这是合理的安全分级设计。

**2. 第三方登录扩展性**
`user_oauth` 表的 `platform` 字段设计为 `VARCHAR(30)` 并以 `(platform, open_id)` 为唯一键，可无缝扩展 Apple/Google/支付宝等登录方式，无需改表结构。

**3. 双 Token 机制**
`user_sessions` 表同时存储 `access_token` + `refresh_token` 及各自过期时间，支持无感刷新，`logout_type` 字段区分了主动登出/被踢出/异地登录等场景，设计完整。

**4. 验证码体系**
`verify_codes` 表的 `type` 字段覆盖了 register/login/reset_pwd/bind_phone/bind_email 五种场景，`is_used + expire_at` 双重防重放，设计合理。

## 二、识别到的具体问题

### 🔴 问题一：注册流程缺乏平台差异化支持

**现状**：`AuthController.register()` 只支持 `username + email + password` 注册，这是 PC 端的注册模式。

```typescript
// 当前 register 方法 - 只有一种注册路径
async register() {
  this.validate({
    username: { type: 'string', min: 3, max: 50 },
    email: { type: 'email' },
    password: { type: 'string', min: 8 },
    // ...
  });
}
```

**缺失的注册方式**：
| 平台 | 期望注册方式 | 当前支持 |
|------|------------|---------|
| 微信小程序 | 微信授权一键登录（无需填表单） | ❌ 无 |
| 移动 H5 | 手机号 + 短信验证码 | ❌ 无 |
| iOS/Android | 手机号/微信/Apple ID | ❌ 无 |
| 官网 PC | 邮箱 + 密码 | ✅ 有 |

**根因**：`auth.ts` 中没有 `wechat-login`（微信静默登录）和 `phone-register`（手机号注册）两个独立接口。

---

### 🔴 问题二：用户信息字段对 C 端场景不完整

**现状**：`users` 表字段主要面向管理后台设计，缺少 C 端用户常用的个人信息字段：

| 缺失字段                | 适用平台  | 说明                         |
| ----------------------- | --------- | ---------------------------- |
| `bio` / `signature`     | 所有 C 端 | 个人简介/签名                |
| `region` / `city`       | H5/小程序 | 用户所在城市（非收货地址）   |
| `language`              | 所有      | 语言偏好（国际化）           |
| `timezone`              | 所有      | 时区（跨时区服务）           |
| `notification_settings` | 移动端    | 推送通知偏好                 |
| `privacy_settings`      | 所有 C 端 | 隐私设置（谁可以看我的信息） |
| `referral_code`         | 所有 C 端 | 邀请码（用于裂变营销）       |
| `invited_by`            | 所有 C 端 | 邀请人 ID                    |
| `points`                | 所有 C 端 | 积分（会员体系基础）         |
| `level`                 | 所有 C 端 | 用户等级                     |

---

### 🔴 问题三：完全缺失会员等级体系

**现状**：`users` 表有 `user_type`（1普通/2管理员/3超级管理员），这是**权限类型**，不是**会员等级**。数据库中没有任何会员相关表。

> 注：`user_type` 字段已于 v2.9 废弃，权限类型由 RBAC `roles` 表管理。

**缺失的会员体系**：

- 会员等级定义表（等级名称、权益、升级条件）
- 用户会员状态表（当前等级、到期时间、积分余额）
- 积分流水表（积分来源、消耗记录）

---

### 🟡 问题四：登录接口缺少平台路由分发

**现状**：`POST /api/auth/login` 是单一入口，通过 `clientId` 区分平台，但 Controller 层没有对不同 `login_type` 做分支处理：

```typescript
// 当前 login 方法 - 只验证 username + password
async login() {
  this.validate({
    username: { type: 'string' },
    password: { type: 'string' },
    clientId: { type: 'string' },
    // 缺少 loginType 字段来区分登录方式
  });
}
```

`login_logs` 表有 `login_type` 字段（password/sms/email/wechat/token），但 Controller 没有对应的处理逻辑。

---

### 🟡 问题五：微信小程序登录流程缺失

微信小程序登录是 **code → session_key → openid** 的特殊流程，需要：

1. 前端调用 `wx.login()` 获取 `code`
2. 后端用 `code` 换取 `openid + session_key`
3. 与 `user_oauth` 表关联，首次登录自动注册

当前没有 `POST /api/auth/wechat-login` 接口，`user_oauth` 表虽然设计好了，但没有对应的 Controller 方法。

---

### 🟡 问题六：`user_type` 与 RBAC 角色体系存在语义重叠

> ✅ **已解决（v2.9，2026-05-12）**：`user_type` 字段已废弃，权限判定统一走 `user_roles` + `roles` 表 RBAC 体系。用户来源平台由 `register_source` 字段标识。详见 [`010_deprecate_user_type.sql`](../../database/010_deprecate_user_type.sql)。

`users.user_type`（1普通/2管理员/3超级管理员）与 `roles` 表（user/admin/super_admin）存在语义重叠，可能导致权限判断逻辑分散在两处，增加维护成本。

## 三、改进方案

### 方案一：用户信息字段扩展（新增 SQL 迁移文件）

**策略**：不修改 `users` 主表（避免影响现有功能），新增 `user_profiles` 扩展表，采用 1:1 关联。

```sql

  `id`                    BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT,
```

### 方案三：登录注册接口扩展方案

按照 `node-api-dev` 规范，需要在 `auth.ts` Controller 中新增以下方法：

```typescript
// 新增接口设计（不影响现有接口）

/** POST /api/auth/phone-register - 手机号注册（H5/iOS/Android） */
async phoneRegister() {
  this.validate({
    phone:    { type: 'string' },
    code:     { type: 'string' },  // 短信验证码
    clientId: { type: 'string' },
    nickname: { type: 'string', required: false },
    platform: { type: 'string', required: false },
  });
  // 1. 验证短信验证码
  // 2. 检查手机号是否已注册
  // 3. 创建用户（username 可自动生成）
  // 4. 返回 Token
}

/** POST /api/auth/phone-login - 手机号验证码登录 */
async phoneLogin() {
  this.validate({
    phone:    { type: 'string' },
    code:     { type: 'string' },
    clientId: { type: 'string' },
    platform: { type: 'string', required: false },
  });
}

/** POST /api/auth/wechat-login - 微信登录（小程序/公众号/开放平台） */
async wechatLogin() {
  this.validate({
    code:      { type: 'string' },  // wx.login() 返回的 code
    clientId:  { type: 'string' },
    platform:  { type: 'string' },  // miniprogram/h5/web
    // 小程序额外字段（可选，用于获取手机号）
    encryptedData: { type: 'string', required: false },
    iv:            { type: 'string', required: false },
  });
  // 1. code 换 openid（调用微信 API）
  // 2. 查 user_oauth 表，找到关联用户
  // 3. 未注册则自动创建用户（静默注册）
  // 4. 返回 Token
}
```

### 优先级建议

| 优先级 | 改进项                                                       | 影响范围             | 工作量 |
| ------ | ------------------------------------------------------------ | -------------------- | ------ |
| **P0** | 新增 `POST /api/auth/wechat-login` 接口                      | 微信小程序上线必须   | 中     |
| **P0** | 新增 `POST /api/auth/phone-login` 接口                       | H5/移动端必须        | 小     |
| **P1** | 新建 `user_profiles` 扩展表 + 对应 Model/Service             | 不影响现有功能       | 小     |
| **P1** | 新建 `member_levels` + `user_members` + `points_logs` 三张表 | 会员体系基础         | 中     |
| **P2** | ~~解决 `user_type` 与 `roles` 语义重叠问题~~                  | ✅ 已于 v2.9 解决  | -     |
| **P2** | 新增 `POST /api/auth/phone-register` 接口                    | 手机号注册           | 小     |

### 关键设计原则

1. **扩展而非修改**：`users` 主表字段已被现有代码引用，新增字段通过 `user_profiles` 1:1 扩展表实现，零破坏性
2. **会员与权限分离**：`user_members.level_code` 控制服务差异化（折扣/功能），`roles` 控制系统权限，两套体系独立演进
3. **`extra` JSON 字段的过渡利用**：`users.extra` 字段可作为 `user_profiles` 正式上线前的临时存储，降低迁移风险

## 一、项目概述

### 1.1 背景

经对当前 super-tools 项目族的全面探索发现：

**后端（super-tool-node）现状**：
- Egg.js 3 + TypeScript 5 + Sequelize 6 + MySQL + Redis（ioredis）
- 不存在统一的通知系统：`alert_logs` 仅落库 + `logger.warn`、`feedback` 回复用户无感知、`verify_code` 直接调用 sms/mail
- 缺失基础设施：**没有 WebSocket、消息队列、邮件能力**；短信仅有 mock 与腾讯云骨架

**管理端（super-tools-admin）现状**：
- UmiJS 4 + Ant Design 5 + DVA + 自研 RBAC（`AuthWrapper`/`AuthButton` + permCode）
- 无任何"通知中心"页面占位

**前端（super-tools-web）现状**：
- Yarn Workspaces monorepo + UmiJS 3 + React 16 + Zustand
- H5（micro-tools）和 PC（tool-box）顶部导航**无消息入口占位**
- 网络层不统一：H5 完整（401 自动刷新），PC 简陋
- **无 WebSocket / socket.io-client 依赖**

**小程序/原生 App**：`super-tools-mini` 目录为空；无任何小程序、iOS、Android 工程。

### 1.2 V2 目标定位

构建一个**务实可落地**的通知系统：
- 站内信 + 邮件 + 短信三渠道统一管理
- 用户偏好/静默/频控防骚扰机制
- 实时推送（WebSocket）+ 多端同步
- 业务方一行代码触发：`ctx.service.notification.send({...})`
- 模块边界清晰，未来可平滑演进为中台

### 1.3 V2 不做的事（明确边界）

| 不做项 | 原因 |
|--------|------|
| App Push（FCM/APNs/国内厂商） | 无原生 App / 小程序工程 |
| 微信模板/订阅消息 | 业务未明确需求 |
| 行为分组 / 用户标签系统 | 无埋点系统 |
| 多租户 SaaS 隔离 | 业务无此需求 |
| AB 测试 / 多语言模板 | YAGNI |
| 模板审核流 | RBAC + 版本快照已足够 |
| 事件总线 / 触发规则引擎 | 业务方同进程直调即可 |
| 模板国际化 i18n | 与现有项目一致暂不做 |

### 1.4 用户角色

| 角色 | 通知模块职责 |
|------|------------|
| 超级管理员 | 系统配置、所有权限 |
| 管理员 | 模板/任务/受众/统计全部能力，除 config:manage |
| 运营 | 创建任务、管理模板（不含发布权）、查看数据 |
| 数据分析师 | 只读 + 报表导出 |
| 普通用户 | 接收通知、管理偏好（C 端） |

## 二、术语与设计决策

### 2.1 术语定义

| 术语 | 说明 |
|------|------|
| 通知（Notification） | 系统向用户发送的消息单元 |
| 渠道（Channel） | 投递媒介，V1 支持：in_app / email / sms |
| 类型（Type） | 通知的业务分类，如 `BUSINESS_FEEDBACK_REPLY` |
| 模板（Template） | 渲染规则；同一类型在不同渠道有不同模板 |
| 受众（Audience） | 通知目标用户集合，支持静态/动态 |
| 任务（Task） | 一次发送活动的容器，含调度配置 |
| 偏好（Preference） | 用户对通知类型 × 渠道的订阅设置 |
| 静默时段（Quiet Hour） | 用户设置的免打扰时间段 |
| 频控（Rate Limit） | 用户/渠道/类型三维度的发送频次限制 |
| 幂等键（Idempotent Key） | 防止重复发送的唯一标识 |

### 2.2 关键设计决策

| # | 决策点 | 选择 |
|---|--------|------|
| 1 | 项目范围 | **务实落地版**（admin/h5/pc 三端，站内信+邮件+短信） |
| 2 | 模板审核流 | **不做**，用 RBAC + 版本快照 + 审计日志 |
| 3 | 用户受众分组 | **务实版**：基础维度 + 保存复用 + 预览人数 |
| 4 | 异步队列 | **BullMQ + Redis**（复用现有 ioredis） |
| 5 | 实时推送 | **egg-socket.io + 房间机制**（按 userId） |
| 6 | 数据看板 | **独立页面 + Dashboard widget 双轨** |
| 7 | 触发式发送 | **内部 API 直调** |
| 8 | 前端网络层 | **抽 `shared/notification-sdk`** |

## 四、数据模型设计

### 4.1 表清单（11 张新表）

全部沿用现有约定：`BIGINT UNSIGNED` 主键、`underscored` 字段、`utf8mb4_unicode_ci` 字符集、`InnoDB` 引擎。

| # | 表名 | 用途 | 数据规模 | 软删 |
|---|------|------|---------|:---:|
| 1 | `notification_types` | 通知类型分层 | ~50 行 | ✅ |
| 2 | `notification_templates` | 消息模板 | ~100-500 行 | ✅ |
| 3 | `notification_template_versions` | 模板版本快照 | templates × 5 | ❌ |
| 4 | `notification_audiences` | 受众分组 | ~50-200 行 | ✅ |
| 5 | `notification_tasks` | 发送任务 | 万级 | ❌ |
| 6 | `notification_messages` | 用户消息记录 | **千万级** | ❌ |
| 7 | `notification_user_preferences` | 用户订阅偏好 | 用户数 × type 数 | ❌ |
| 8 | `notification_user_quiet_hours` | 用户全局免打扰 | ≤ 用户数 | ❌ |
| 9 | `notification_rate_limit_config` | 频控配置 | <50 行 | ❌ |
| 10 | `notification_channel_configs` | 渠道服务商配置 | <20 行 | ❌ |
| 11 | `notification_send_logs` | 单次下发日志 | **千万级** | ❌ |

> **关键设计**：`messages` 与 `send_logs` 分开 — 前者是"用户视角的站内信"，后者是"每渠道下发动作的审计日志"。一条消息发到 3 个渠道 = 1 条 messages + 3 条 send_logs。

**`dynamic_rules` JSON 结构**：

```json
{
  "operator": "and",
  "conditions": [
    { "field": "user.status",       "op": "eq",  "value": 1 },
    { "field": "user.created_at",   "op": "gte", "value": "2024-01-01" },
    { "field": "user.last_login_at","op": "gte", "value": "P30D" },
    { "field": "member.level_id",   "op": "in",  "value": [3, 4, 5] },
    { "field": "member.expire_at",  "op": "lte", "value": "P7D" },
    { "field": "role.code",         "op": "in",  "value": ["vip"] },
    { "field": "device.platform",   "op": "in",  "value": ["ios"] },
    { "field": "favorite.tool_id",  "op": "eq",  "value": 12345 }
  ]
}
```

**支持字段白名单**（V1）：
- `user.status` / `user.created_at` / `user.last_login_at`
- `member.level_id` / `member.plan_code` / `member.expire_at`
- `role.code` / `role.id`（一对多 EXISTS 子查询）
- `device.platform`（关联 `user_devices`）
- `favorite.tool_id`（关联 `user_tool_favorites`）

**操作符**：`eq` / `ne` / `gt` / `gte` / `lt` / `lte` / `in` / `nin` / `between`。  
**相对时间**：`P30D` 表示"最近 30 天"。  
**嵌套深度**：最多 3 层。

### 6.1 发送主链路（Pipeline）

```
┌─────────────────────────────────────────────────────────────────┐
│  调用方：ctx.service.notification.send({ templateCode, ... })    │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
      ┌─────────────[ 同步阶段 ]────────────────┐
      │ ① 参数校验                             │
      │ ② 模板查询 + 渠道筛选（按 channels × 已发布模板）│
      │ ③ 接口幂等检查（Redis SETNX 5min）        │
      │ ④ 用户偏好检查（强制类型豁免）            │
      │ ⑤ 频控检查（user / channel / type）       │
      │ ⑥ 静默时段检查（按用户时区）              │
      │ ⑦ 模板渲染（变量替换）                  │
      │ ⑧ 写入 notification_messages            │
      └─────────────────────┬───────────────────┘
                            │ 返回 { messageId, status: 'queued' }
                            ▼
                  enqueue → BullMQ Queue
                            │
      ┌──────────[ 异步阶段：BullMQ Worker ]────┐
      │ ⑨ 队列消费（按 priority 排序）           │
      │ ⑩ 渠道并发分发                         │
      │ ⑪ 写 send_logs                       │
      │ ⑫ Socket.IO emit 实时推送             │
      └─────────────────────┬───────────────────┘
                            │
                            ▼
                  失败重试（指数退避） → 死信
```

**阶段失败处理**：

| 阶段 | 失败行为 |
|------|---------|
| ①②③ | 抛异常给调用方 |
| ④⑤⑥ | 不抛异常，写 send_logs `status=skipped`，返回 `{ status: 'skipped', skipReason }` |
| ⑦ | 渲染严格模式抛异常；宽松模式保留占位符 + WARN |
| ⑧ | 唯一键冲突 → 返回原 message_id（幂等命中） |
| ⑨⑩⑪ | 写 send_logs `status=failed`；触发重试 |
| ⑫ | Socket 推送失败不影响消息状态（用户下次拉取仍可见） |

**全部跳过时**：`anyAllowed=false` → **不写 messages**，仅在 send_logs 中记录 skipped（避免污染用户消息列表）。

### 6.2 模板渲染规范

**变量语法**：`{{variable.path}}`

**渲染引擎**：自实现轻量替换器（不引 Handlebars，避免模板注入 + 减少依赖）。

```ts
function render(template: string, variables: Record<string, any>): {
  result: string; missingVars: string[]; warnings: string[];
} {
  const missing: string[] = [];
  const result = template.replace(/\{\{([\w.]+)\}\}/g, (match, path) => {
    const value = getByPath(variables, path);
    if (value === undefined) { missing.push(path); return match; }
    return escape(String(value));   // HTML 渠道做 escape
  });
  return { result, missingVars: missing, warnings: [] };
}
```

**系统内置变量**（自动注入）：
- `system.time` / `system.date` / `system.platform`
- `user.name` / `user.phone`（脱敏）/ `user.email`（脱敏）

**关键约束**：用户传入的 variables **不参与二次解析**（防模板注入攻击）。

// app/io/middleware/auth.ts
export default app => async (ctx, next) => {
  const token = ctx.socket.handshake.auth?.token 
             || ctx.socket.handshake.headers?.authorization?.replace('Bearer ', '');
  if (!token) return ctx.socket.disconnect(true);
  try {
    const payload = app.jwt.verify(token, app.config.jwt.secret);
    const isBlacklisted = await app.redis.get(`token:blacklist:${payload.jti}`);
    if (isBlacklisted) return ctx.socket.disconnect(true);
    ctx.socket.userId = payload.userId;
    ctx.socket.join(`user:${payload.userId}`);
    if (payload.scope === 'admin') ctx.socket.join('admin:dashboard');
    await next();
  } catch (e) {
    ctx.socket.disconnect(true);
  }
};

## 七、频控/静默/优先级矩阵

### 7.1 主决策算法

```ts
async function shouldDeliver(input: SendInput): Promise<DecisionResult> {
  const { userId, typeId, channels, priority, bypassPreference } = input;
  const decisions: ChannelDecision[] = [];
  
  const userPref = await preferenceService.getUserPreferences(userId, typeId);
  const quietHours = await preferenceService.getQuietHours(userId);
  const type = await typeService.get(typeId);

  for (const channel of channels) {
    const decision = { channel, allow: true, skipReason: null };

    // ===== Layer 1：偏好检查 =====
    if (!bypassPreference) {
      if (userPref.global_enabled === false && type.user_cancelable) {
        decision.allow = false; decision.skipReason = 'unsubscribed_global';
        decisions.push(decision); continue;
      }
      const subscribed = userPref.types[typeId]?.channels?.[channel]
                      ?? type.default_channels.includes(channel);
      if (!subscribed && type.user_cancelable) {
        decision.allow = false; decision.skipReason = 'unsubscribed_channel';
        decisions.push(decision); continue;
      }
    }

    // ===== Layer 2：静默时段 =====
    if (quietHours.enabled && priority > 0) {
      const inQuiet = isInQuietWindow(quietHours, new Date());
      if (inQuiet && !(priority === 0 && quietHours.receive_urgent)) {
        decision.allow = false; decision.skipReason = 'quiet_hour';
        decisions.push(decision); continue;
      }
    }

    // ===== Layer 3：频控 =====
    if (priority > 0) {
      const rl = await rateLimitService.check({ userId, channel, typeCode: type.code, priority });
      if (!rl.allowed) {
        decision.allow = false; decision.skipReason = 'rate_limited';
        decision.rule = rl.rule;
        decisions.push(decision); continue;
      }
    }
    decisions.push(decision);
  }

  return {
    decisions,
    anyAllowed: decisions.some(d => d.allow),
    allSkipped: decisions.every(d => !d.allow),
  };
}
```

**关键约束**：
- **顺序固定**：偏好 → 静默 → 频控（短路返回）
- **`bypassPreference=true` 仅 P0 + 强制类型可用**（service 层校验，普通业务方传也无效，写 WARN 日志，错误码 108505）
- **每渠道独立决策**
- **任一渠道通过即写消息**；**全部跳过则不写 messages**，仅写 send_logs（skipped）

### 7.2 静默窗口判定

```ts
function isInQuietWindow(qh: QuietHours, now: Date): boolean {
  if (!qh.enabled || !qh.start || !qh.end) return false;
  const userNow = moment(now).tz(qh.timezone);
  const today = userNow.format('YYYY-MM-DD');
  const start = moment.tz(`${today} ${qh.start}`, 'YYYY-MM-DD HH:mm', qh.timezone);
  let end = moment.tz(`${today} ${qh.end}`, 'YYYY-MM-DD HH:mm', qh.timezone);
  
  if (start.isBefore(end)) {
    return userNow.isBetween(start, end, undefined, '[)');
  } else {
    if (userNow.isSameOrAfter(start)) return true;
    const yesterdayStart = start.clone().subtract(1, 'day');
    return userNow.isBetween(yesterdayStart, end, undefined, '[)');
  }
}
```

**测试用例**：
- 同日窗口 12:00-14:00：13:00 命中 / 14:00 不命中（左闭右开）
- 跨天窗口 22:00-08:00：23:30 命中 / 07:00 命中 / 08:00 不命中
- 时区差异：用户在 Asia/Shanghai，UTC 14:00 = 当地 22:00 → 命中

### 7.3 频控 Redis Key 与 Lua 脚本

**Key 命名**：

```
notify:rl:{scope}:{userId}:{target}:{window}:{bucket}

scope:    user / channel / type
target:   user 时为 "_"；channel 时为 channel code；type 时为 type code
window:   hour / day / week
bucket:   时间桶（防止跨窗口边界双计），格式：
          hour  → YYYYMMDDHH
          day   → YYYYMMDD
          week  → YYYY[W]WW（ISO 周）
```

**示例**：
- `notify:rl:user:12345:_:hour:2026051517`
- `notify:rl:channel:12345:sms:day:20260515`
- `notify:rl:type:12345:MARKETING_ACTIVITY:week:2026W20`

**Lua 脚本（原子检查 + 自增）**：

```lua
-- KEYS[1] = redis key
-- ARGV[1] = max_count
-- ARGV[2] = ttl_seconds
-- 返回值：{allowed(0/1), current}
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current >= tonumber(ARGV[1]) then
  return {0, current}
end
local newVal = redis.call('INCR', KEYS[1])
if newVal == 1 then
  redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))
end
return {1, newVal}
```

**回滚逻辑**：任一规则拒绝时，已 INCR 的规则需 DECR 回滚（保持精确）。

### 7.4 优先级矩阵（最终版，SSOT）

> 本表是开发、测试、文档、用户帮助页面的**唯一真理来源**。

| 优先级 | 类型示例 | 偏好 | 静默 | 频控 | 队列 priority | 重试 | 备注 |
|:---:|---|:---:|:---:|:---:|:---:|:---:|---|
| **P0** | 账号安全/异常登录/密码修改/验证码 | ❌跳过 | ❌跳过 | ❌跳过 | 1 | 5 次（10s 起步） | 强制送达 |
| **P1** | 反馈回复/会员到期 | 部分 | 部分 | 可豁免 | 5 | 3 次 | 重要业务 |
| **P2** | 工具上下架/积分变动 | ✅ | ✅ | ✅ | 10 | 3 次 | 普通业务 |
| **P3** | 营销活动/推荐 | ✅ | ✅严格 | ✅严格 | 20 | 2 次 | 防骚扰为主 |

**关键不变量**：
1. **P0 永远不被跳过**（除非用户显式 `receive_urgent=false`）
2. **P3 永远受全局静默限制**（即使用户没开免打扰，22:00-08:00 也不发）
3. **`skip_priority` 只能放宽，不能收紧**

### 7.5 端到端跟踪示例

#### 场景 1：会员到期前 7 天提醒（P1 多渠道）

**输入**：

```ts
{
  templateCode: 'BUSINESS_MEMBER_EXPIRE_SOON',
  userId: 12345,
  channels: ['in_app', 'email', 'sms'],
  priority: 1,
}
```

**用户状态**：BUSINESS_MEMBER_EXPIRE_SOON 类型订阅：in_app ✅ / email ✅ / sms ❌；免打扰 22:00-08:00；当前 23:30。

**决策**：

| 渠道 | 偏好 | 静默 | 频控 | 最终 |
|------|:---:|:---:|:---:|:---:|
| in_app | ✅ | ❌ in quiet, P1 | — | **跳过 quiet_hour** |
| email | ✅ | ❌ in quiet, P1 | — | **跳过 quiet_hour** |
| sms | ❌ unsubscribed | — | — | **跳过 unsubscribed_channel** |

**结果**：`anyAllowed=false` → **不写 messages**，3 条 send_logs 标 skipped。

#### 场景 2：异常登录提醒（P0 强制送达）

**输入**：`{ priority: 0, bypassPreference: true }`，用户已关闭所有通知 + 当前在静默期 + 频控均超限。

**决策**：3 个渠道全部送达（P0 跳过偏好/静默/频控）。

#### 场景 3：营销活动推送（P3 严格防骚扰）

**输入**：营销类，当前 14:00。**用户状态**：MARKETING_ACTIVITY 类型 in_app ✅ / email ❌；本周营销类已 3/3 条。

**决策**：in_app 因 type 频控 skip；email 因 unsubscribed skip。

#### 场景 4：批量营销发送（10 万人）

**任务流转**：
1. 同步：写 task + audience_snapshot；enqueue 到 broadcast 队列（含 30 秒 delay）
2. broadcast worker：分批拉受众（每批 1000）→ 主决策 → 过则写 message + enqueue 到 send 队列
3. send-worker（50 并发）：调用 ChannelAdapter → 写 send_log → 更新 task counts
4. 进度：每 100 条 emit `task:progress` 到 `task:42` 房间
5. 完成：emit `task:completed`

**异常处理**：
- Redis 重启：schedule 兜底每分钟扫表恢复 stuck
- 邮件服务商失败：渠道熔断后续 message 邮件渠道全 skip
- admin 暂停：worker 检测 task.status=paused 时停止取新 job
- admin 取消（30 秒内）：所有未消费 send job 标记 cancelled

### 7.6 跳过原因（skip_reason）枚举

供 send_logs 与统计分析使用，**禁止扩展**：

| skip_reason | 含义 | 计入"跳过率" |
|------------|------|:---:|
| `unsubscribed_global` | 用户全局关闭通知 | ✅ |
| `unsubscribed_channel` | 用户关闭此类型此渠道 | ✅ |
| `quiet_hour` | 命中静默时段 | ✅ |
| `rate_limited` | 命中频控规则 | ✅ |
| `invalid_target` | 用户无邮箱/手机号 | ❌（计为失败） |

| `idempotent_hit` | 幂等键命中（去重） | 单独统计 |

| `all_channels_blocked` | 所有渠道都被跳过（聚合状态） | — |

### 8.3 关键页面交互设计

#### 8.3.1 模板管理 — 编辑器

- **左右分屏**：左侧表单 + 富文本编辑器；右侧实时渲染预览
- **变量插入辅助**：编辑器顶部工具栏"插入变量"下拉
- **渠道分页 Tab**：站内信/邮件/短信各自独立标题和正文（短信 Tab 隐藏标题字段）
- **变量校验**：保存时静态扫描内容中的 `{{var}}`，提示哪些变量未在 sample_variables 中定义
- **预览强制**：点击"发布"前必须先点过"预览"按钮（前端临时禁用控制）

**版本历史 Drawer**：
- 时间轴展示历史版本（最新在上）
- 每版本显示 `change_note` + 发布者 + 发布时间
- "查看 diff" 按钮 → Modal 中用 `react-diff-viewer` 风格的左右对比
- "回滚到此版本" → 弹确认 Modal，输入回滚原因（写入新版本的 change_note）

#### 8.3.2 受众分组 — 规则编辑器

```
[+] 添加条件组（AND）
  ├─ 用户.状态 [等于] [启用] [×]
  ├─ 会员.等级 [属于] [选择: VIP金/VIP银] [×]
  └─ [+] 嵌套组（OR）
     ├─ 用户.最近登录 [≥] [最近30天] [×]
     └─ 用户.注册时间 [介于] [2024-01-01 ~ 2024-12-31] [×]

[+ 添加条件] [+ 添加嵌套组]

------- 实时预览 -------
预计触达：12,345 人  [刷新]   ⓘ 估算值（>100万）
[抽样 10 人查看]
```

- 字段下拉**联动**：选了 `member.level_id` 后，操作符限定为 `eq`/`in`，值控件变多选下拉
- 嵌套深度限制：最多 3 层
- 保存校验：空规则不能保存；条件值类型必须匹配字段类型

#### 8.3.3 发送任务 — 创建向导

4 步向导（`Steps` + 内嵌表单）：

```
Step 1：选择模板
Step 2：选择受众
Step 3：填写变量
Step 4：调度配置 + [✔] 我已确认
        [取消] [创建任务]
```

**创建后**：
- 30 秒倒计时撤销按钮
- 跳转到任务详情页，自动订阅 socket 事件 `task:progress` 实时显示进度条

#### 8.3.4 队列监控 Tab

显示三个队列健康度（等待/活跃/完成/失败数）+ 死信任务列表（手动重试/丢弃）。前端每 10 秒刷新。

| 图标 | 内置图标走 IconFont 字体；自定义图标懒加载 |
| socket 重连 | 指数退避 1s → 2s → 4s → ...最多 60s |
| 离线检测 | `navigator.onLine` + socket disconnect 双重判断 |

### 9.6 一致性要点

- 未读数实时同步（多端 + 多页签）
- 已读/归档动作多端同步
- 偏好修改实时生效（无需重连）
- token 刷新自动重连 socket
- 登出主动断开 socket

### 10.6 Socket 客户端模块

```ts
export interface NotificationSocket {
  readonly status: 'idle' | 'connecting' | 'connected' | 'disconnected' | 'fallback';
  
  connect(): Promise<void>;
  disconnect(): void;
  reconnect(): Promise<void>;
  
  /** 订阅事件，返回 unsubscribe 函数 */
  on<E extends SocketEventName>(event: E, handler: (payload: SocketEventMap[E]) => void): () => void;
  once<E extends SocketEventName>(event: E, handler: (payload: SocketEventMap[E]) => void): void;
  off<E extends SocketEventName>(event: E, handler?: (payload: SocketEventMap[E]) => void): void;
  
  /** 订阅特定任务进度（admin 用） */
  subscribeTask(taskId: number): () => void;
  
  isFallback(): boolean;
}
```

**重连策略**：

```
attempt 1: 1s    attempt 2: 2s    attempt 3: 4s
attempt 4: 8s    attempt 5: 16s   attempt N≥6: 60s（最大）
```

每次重连尝试都重新获取最新 token（应对 token 已刷新的场景）。

**降级策略**：
- 触发条件：连续 3 次连接失败 OR 连接成功但 30 秒内无任何 ping
- 降级行为：每 60 秒调用 `api.unreadCount()`，与 socket 事件 emit 相同的 callback
- 升级回归：每 5 分钟尝试重连 socket，成功后退出降级
- 状态对外暴露 `socket.isFallback()`，可用于 UI 显示"使用普通模式"提示

#### 11.2.4 会员到期定时任务（`app/schedule/notificationMemberExpire.ts`，新增）

```ts
import { Subscription } from 'egg';

export default class MemberExpireNotify extends Subscription {
  static get schedule() {
    return { cron: '0 0 9 * * *', type: 'worker' };
  }

  async subscribe() {
    const today = moment().startOf('day');
    
    // 1. 即将到期：剩 7/3/1 天
    for (const days of [7, 3, 1]) {
      const targetDate = today.clone().add(days, 'days');
      const members = await this.ctx.model.UserMember.findAll({
        where: {
          expire_at: { [Op.gte]: targetDate.toDate(), [Op.lt]: targetDate.clone().add(1, 'day').toDate() },
          status: 1,
        },
      });
      
      for (const m of members) {
        this.ctx.service.notification.send({
          templateCode: 'BUSINESS_MEMBER_EXPIRE_SOON',
          userId: m.user_id,
          channels: days === 1 ? ['in_app', 'email', 'sms'] : ['in_app', 'email'],
          variables: {
            'member.level_name': m.level_name,
            'member.expire_at': moment(m.expire_at).format('YYYY-MM-DD'),
            'member.days_left': days,
          },
          extra: { link_url: '/member' },
          idempotentKey: `member-expire-soon-${m.user_id}-${today.format('YYYYMMDD')}-${days}d`,
          priority: 1,
        }).catch(err => this.ctx.logger.error('[notify] member expire failed', { userId: m.user_id, err }));
      }
    }
    
    // 2. 已过期（昨天到期）
    const yesterdayMembers = await this.ctx.model.UserMember.findAll({...});
    for (const m of yesterdayMembers) {
      this.ctx.service.notification.send({
        templateCode: 'BUSINESS_MEMBER_EXPIRED',
        userId: m.user_id,
        channels: ['in_app', 'email'],
        variables: { 'member.level_name': m.level_name },
        extra: { link_url: '/member/renew' },
        idempotentKey: `member-expired-${m.user_id}-${today.format('YYYYMMDD')}`,
        priority: 1,
      }).catch(err => this.ctx.logger.error('[notify] member expired failed', err));
    }
  }
}
```

**关键设计**：09:00 执行（避开静默期）；`type: 'worker'`（多机部署仅一个 worker 执行）；幂等键带天数。大量场景应改为 `sendByAudience`。

## 十二、代码规范条款

> **【必读】通知发送代码规范**

1. **非阻塞**：业务流程中调用 `notification.send()` **不得阻塞主流程**。即使发送失败，业务流程必须正常完成。
2. **统一 `.catch` 兜底**：所有调用都必须包裹错误捕获：
   ```ts
   ctx.service.notification.send({...}).catch(err => 
     ctx.logger.error('[notify] send failed', { templateCode, userId, err })
   );
   ```
3. **不要 `await` 在主流程**：除非业务必须等待发送结果（极少数场景，如发验证码并等待 sendDirect 返回）。
4. **幂等键必传**：所有触发式调用必须传 `idempotentKey`，命名规范 `{业务前缀}-{业务ID}-{操作类型}`。
5. **变量命名**：变量 key 使用点路径（`order.id` 而非 `orderId`），与模板占位符 `{{order.id}}` 对齐。
6. **优先级**：业务方不应自行决定 priority，由模板/类型继承；仅 P0 系统类可显式覆盖（且需具备 admin 权限）。
7. **严禁绕过**：业务代码不得直接写 `notification_messages` 表；不得直接调用 `mailService.send()` 或 `smsService.send()`，所有发送必须经过通知系统统一管线。
8. **测试**：触发点改造必须添加 e2e 用例验证（mock notification service 的 `send` 调用）。
9. **`bypassPreference` 滥用防护**：service 层强制校验"非 P0 + 普通类型"传 true 时拒绝并记 WARN。
10. **`sendDirect` 仅限验证码**：service 层硬编码白名单校验，仅 `VERIFY_CODE_*` 模板可用。
11. **审计**：所有模板/任务/配置变更通过 admin API 的操作必须写入 `audit_logs`。
12. **日志规范**：通知相关日志统一前缀 `[notify]`，便于后续聚合查询。

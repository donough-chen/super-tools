# 积分与成长体系深度评估报告

## 一、方案定性评价

**强解耦方案选择正确**，理由你文档里已经写得很充分，我完全认同。核心补充一点：

```
成长值 = 用户对平台的"历史贡献度量"
积分   = 平台给用户的"即时激励货币"

两者混用的最大风险不是数学问题，而是：
用户会用"刷积分"的心态来"刷等级"，破坏等级的社交信号价值
```

## 二、行为奖励矩阵逐条审查

### 🔴 问题条目

**问题 1：注册 +10 成长值 —— 与强解耦原则冲突**

```
你的规则：成长值只来自"长期价值行为"
注册是一次性行为，不代表长期价值

建议方案：
├── 选项 A：注册只给积分（+10），成长值改为 0
└── 选项 B：保留 +10 成长值，但语义改为"账号存在本身的基础资历"
            需要在文档里单独解释，增加理解成本

推荐选项 A，保持规则纯粹性
```

**问题 2：完善资料 +20 成长值 —— 同上，存在争议**

```
完善资料是一次性操作，不是持续价值行为
但它确实影响平台数据质量，有一定"贡献"属性

建议：
├── 降低至 +5 成长值（象征性认可，不影响等级曲线）
└── 或改为：完善资料后"解锁成长值加速"权益，而非直接给成长值
```

**问题 3：连续签到奖励给成长值 —— 轻微违反原则**

```
连续签到 7 天  → +5 成长值
连续签到 30 天 → +20 成长值

签到属于"短期运营行为"，按你的规则不应给成长值
但连续 30 天签到确实体现了"长期活跃"，有一定合理性

建议折中：
├── 7 天连签：成长值改为 0（频率太低，不代表长期价值）
└── 30 天连签：保留 +20（连续 30 天是真实活跃的有力证明）
    可以加一条：连续 365 天签到 → +200 成长值（年度忠诚奖励）
```

**问题 4：新手任务 +10 积分、成长值 0 —— 数值偏低，激励不足**

```
新手任务的核心目的是"让用户完成关键行为路径"
+10 积分对比注册 +10，没有体现"完成任务"的额外价值

建议：
├── 积分提升至 +15～+20（高于注册，体现行为深度）
└── 如果任务涉及首次消费类行为，可以给 +5 成长值
    （首次使用核心功能 = 长期价值行为的起点）
```

**问题 5：提交有效反馈 —— "不限"频次有风险**

```
"被采纳"的判定标准是什么？谁来审核？多久反馈结果？

风险：
├── 用户批量提交低质量反馈，期待被采纳
├── 审核周期长，用户体验差
└── 运营人员审核压力大

建议：
├── 频次限制改为：每月上限 3 次被采纳奖励
├── 增加"提交反馈"本身的即时奖励（+2 积分，不限次数）
│   "被采纳"再额外 +18 积分（总计 +20，拆分即时反馈和质量奖励）
└── 成长值 +5 保留（有效反馈确实是长期价值行为）
```

### 🟡 缺失的重要行为

**缺失 1：首次消费 —— 转化漏斗最关键节点**

| 行为                 | 积分 | 成长值 | 频次 | 理由                                   |
| -------------------- | ---- | ------ | ---- | -------------------------------------- |
| 首次消费（任意金额） | +50  | +30    | 1 次 | 从"注册用户"到"付费用户"是最重要的转化 |

```
注意：首次消费的积分/成长值 与 "消费 1 元 = +1/+1" 叠加发放
即：首次消费 50 元 = +50（消费返）+ +50（首单奖励）= +100 积分
这个叠加要在规则里明确，避免用户误解
```

**缺失 2：消费里程碑 —— 提升 LTV 的核心杠杆**

| 行为               | 积分 | 成长值 | 频次     | 说明             |
| ------------------ | ---- | ------ | -------- | ---------------- |
| 累计消费满 100 元  | +50  | +30    | 里程碑×1 | 阶梯触发，非重复 |
| 累计消费满 500 元  | +150 | +100   | 里程碑×1 | 同上             |
| 累计消费满 2000 元 | +500 | +300   | 里程碑×1 | 同上             |

```
里程碑设计原则：
├── 与等级升级节点错开（不要消费到 500 元刚好升级，再给里程碑奖励，太爽了）
└── 里程碑积分不计入成长值升级判定（避免双重加速）
    ↑ 这条看你的等级升级是否用 total_points 还是 growth_value 判定
```

**缺失 3：订阅/续费行为**

| 行为              | 积分 | 成长值 | 频次     | 说明         |
| ----------------- | ---- | ------ | -------- | ------------ |
| 首次开通会员/订阅 | +100 | +80    | 1 次     | 高价值转化   |
| 每次续费          | +50  | +30    | 每次续费 | 奖励持续付费 |

**缺失 4：年度活跃奖励 —— 成长值体系的"年检"**

| 行为                              | 积分 | 成长值 | 频次      | 说明             |
| --------------------------------- | ---- | ------ | --------- | ---------------- |
| 年度活跃（自然年内登录 180 天）   | +200 | +100   | 每年 1 次 | 奖励真实长期用户 |
| 年度消费达标（自然年消费 ≥ X 元） | +300 | +150   | 每年 1 次 | 保级/升级激励    |

## 三、数值平衡性验证

### 等级升级路径模拟

```
假设等级门槛（你的种子数据）：
白银：500 成长值
黄金：2000 成长值
铂金：5000 成长值
钻石：10000 成长值
```

**场景 A：纯签到用户（不消费）**

```
每日签到：0 成长值
连续 7 天：+5 成长值  × 52 周 = 260/年
连续 30 天：+20 成长值 × 12 次 = 240/年（理想情况）
注册+资料：+30 成长值（一次性）

年度成长值上限 ≈ 530（仅够升白银，且需要完美签到）
→ ✅ 合理，签到用户永远是白银，符合"等级保值"目标
```

**场景 B：活跃消费用户**

```
消费 1 元 = +1 成长值
升白银（500）= 消费 500 元
升黄金（2000）= 累计消费 2000 元
升铂金（5000）= 累计消费 5000 元
升钻石（10000）= 累计消费 10000 元

加上邀请奖励（每邀请 1 人首消 = +50 成长值）：
邀请 10 人首消 = +500 成长值（相当于消费 500 元）
→ ✅ 邀请是有效的升级加速路径，但不会破坏等级稀缺性
```

**场景 C：刷量风险验证**

```
邀请刷量极端情况：
注册 100 个小号 → +30×100 = 3000 成长值（直接黄金）
⚠️ 这是最大风险点

建议：
邀请好友注册的成长值，改为"好友首次消费后才结算"
即：被邀请好友首次消费 → 邀请人 +50 成长值（现有条目）
   邀请好友注册 → 邀请人 +30 积分（不给成长值）
```

## 四、规则完整性补充

### 缺失的边界规则

**1. 积分抵扣上限**

```
需要明确：单笔订单最多可用积分抵扣多少？

常见方案：
├── 固定比例：最多抵扣订单金额的 20%
├── 固定上限：单笔最多抵扣 50 积分
└── 等级差异：白银 10%，黄金 20%，铂金 30%，钻石 50%

不设上限的风险：用户攒够积分后直接 0 元购，影响营收
```

**2. 积分获取上限（防刷）**

```
建议补充每日积分获取上限：

| 来源 | 每日上限 |
|------|---------|
| 签到类 | 已有频次限制，无需额外上限 |
| 消费类 | 不限（消费越多越好） |
| 任务类 | 每日最多获取 50 积分 |
| 邀请类 | 每日最多结算 5 笔邀请奖励 |
```

**3. 积分过期的 FIFO 细节**

```
12 个月 FIFO 过期需要明确：

├── 过期时间起点：积分"获得日"还是"所在自然月最后一天"？
│   建议：获得日起 365 天（精确 FIFO）
├── 消耗时优先扣除哪部分？
│   建议：优先扣除最早获得的积分（FIFO 消耗）
├── 过期提醒节点：
│   ├── 提前 30 天：站内信 + Push
│   ├── 提前 7 天：短信（如有）
│   └── 过期当天：账单通知
└── 过期积分是否可以"激活"？
    建议：不可激活，但可以设计"积分续期任务"
    （如：完成一次消费，当月到期积分延期 90 天）
```

## 三、核心权益详细说明

### 🔑 权益 1：消费积分倍率（最核心）

```
基础规则：消费 1 元 = +1 积分（1×）

等级加成后：
├── 🥈 白银：消费 1 元 = +1.2 积分
├── 🥇 黄金：消费 1 元 = +1.5 积分
├── 💎 铂金：消费 1 元 = +2 积分
└── 👑 钻石：消费 1 元 = +3 积分

实际返现率对比：
青铜  1.0% 返现
白银  1.2% 返现
黄金  1.5% 返现
铂金  2.0% 返现
钻石  3.0% 返现

⚠️ 注意：倍率加成只影响积分，不影响成长值
成长值始终按 1 元 = +1 成长值 计算（避免高等级用户加速升级）
```

### 🔑 权益 2：积分有效期延长

```
这是成长值体系"永不过期"与积分体系"12 个月过期"之间的桥梁

青铜/白银：12 个月（标准）
黄金：     15 个月（+3 个月）
铂金：     18 个月（+6 个月）
钻石：     24 个月（+12 个月）

实现方式：
用户升级时，系统将现有积分的过期时间统一延长至新等级标准
降级时（如有）：不缩短已有积分的过期时间（避免用户投诉）
```

### 🔑 权益 3：每日签到积分加成

```
与行为奖励矩阵联动：

等级    基础签到  连续7天  连续30天
青铜    +1       +20      +100
白银    +2       +24      +120（+20%）
黄金    +3       +28      +140（+40%）
铂金    +5       +32      +160（+60%）
钻石    +10      +40      +200（+100%）

实现建议：
签到基础值按等级读取，连续奖励按比例加成
字段：sign_in_base_points = f(user_level)
```

### 🔑 权益 4：升级礼包

```
触发时机：成长值首次达到门槛时，系统自动发放

🥈 白银礼包：+200 积分（价值 2 元）
🥇 黄金礼包：+500 积分（价值 5 元）
💎 铂金礼包：+1000 积分（价值 10 元）
👑 钻石礼包：+2000 积分（价值 20 元）

礼包积分的过期时间：发放日起按当前等级有效期计算
礼包成长值：不计入升级判定（避免连锁升级）
```

## 二、核心业务逻辑

### 2.1 消费积分实时倍率计算

```
标准流程：

用户下单
  │
  ├─ 读取 users.points_multiplier（当前倍率）
  │
  ├─ 计算应得积分
  │   base_points    = floor(order_amount)        // 消费金额取整
  │   bonus_points   = floor(base_points × (multiplier - 1.0))
  │   total_points   = base_points + bonus_points
  │
  ├─ 写入 points_logs
  │   ┌─────────────────────────────────────────────┐
  │   │ type: 'consume_base'   points: +base_points  │  // 基础消费返积分
  │   │ type: 'consume_bonus'  points: +bonus_points │  // 等级倍率加成
  │   └─────────────────────────────────────────────┘
  │   两条日志分开记录，方便运营分析倍率成本
  │
  └─ 写入 growth_value（始终 +1/元，不受倍率影响）
```

```
数值示例：

黄金用户消费 200 元（倍率 1.5×）：
  base_points  = 200
  bonus_points = floor(200 × 0.5) = 100
  total_points = 300 积分

成长值：+200（不受倍率影响）

积分日志：
  [consume_base]  +200 积分  过期时间: now + 456天
  [consume_bonus] +100 积分  过期时间: now + 456天
```

### 2.2 升级检测流程

```
触发时机：任何导致 growth_value 增加的操作完成后

流程：

growth_value 更新
  │
  ├─ 查询 member_levels WHERE min_growth <= new_growth
  │   ORDER BY min_growth DESC LIMIT 1
  │   → 得到 new_level
  │
  ├─ 对比 users.level_id
  │   ┌── 相同 → 无需处理，结束
  │   └── 不同（new_level > current_level）→ 触发升级
  │
  └─ 升级事务（TRANSACTION）
      ├─ UPDATE users SET
      │    level_id          = new_level.id,
      │    points_multiplier = new_level.points_multiplier
      │
      ├─ INSERT user_level_snapshots（记录升级快照）
      │
      ├─ 发放升级礼包
      │   ├─ 积分：INSERT points_logs
      │   │   type     : 'upgrade_gift'
      │   │   points   : +gift_points
      │   │   growth   : 0              ← D2: 不计入成长值
      │   │   expire_at: now + new_level.points_validity_days
      │   │
      │   └─ 成长值：直接写入 users.growth_value
      │       ⚠️ 写入后不再触发升级检测（D2 的实现关键）
      │       实现方式：用 flag 标记本次为礼包写入，跳过检测
      │
      ├─ 延长现有积分有效期（D4: 历史用户立即生效）
      │   UPDATE points_logs
      │   SET expire_at = GREATEST(
      │     expire_at,
      │     NOW() + INTERVAL new_level.points_validity_days DAY
      │   )
      │   WHERE user_id = ? AND status = 'active'
      │   ⚠️ 用 GREATEST 确保只延长不缩短
      │
      └─ 推送升级通知
          站内信 + Push（异步队列处理）
```

### 2.3 历史用户立即生效（D4）

```
触发场景：系统上线时，历史用户根据现有 growth_value 批量匹配等级

批量脚本逻辑：

FOR EACH user:
  1. 根据 growth_value 匹配 level_id
  2. UPDATE users SET level_id, points_multiplier
  3. 延长积分有效期（同升级流程）
  4. ⚠️ 不发放升级礼包（历史用户跳过礼包，避免大规模积分发放）
     或：仅发放最终等级礼包（运营决策）

建议：历史用户不补发礼包，但在 APP 内展示"您已是 XX 等级"
     配合一次性"老用户专属权益激活"活动作为补偿
```

## 四、完整业务规则文档

### 4.1 等级规则

```
1. 升级规则
   - 成长值达到对应门槛时，系统实时自动升级
   - 升级立即生效，无需等待审核

2. 降级规则
   - 永不降级（D3）
   - 成长值只增不减，等级只升不降

3. 升级礼包
   - 升级时自动发放，无需领取
   - 礼包积分有效期：发放日起按新等级有效期计算
   - 礼包成长值：计入 growth_value，但不触发二次升级检测

4. 历史用户
   - 系统上线时根据现有成长值自动匹配等级
   - 立即享受对应等级全部权益
```

### 4.2 积分倍率规则

```
1. 倍率计算
   - 基础积分：floor(消费金额)，1 元 = 1 积分
   - 倍率加成：floor(基础积分 × (倍率 - 1.0))
   - 两部分分开记录，合并展示

2. 倍率生效时机
   - 订单完成（非下单时）触发积分发放
   - 退款时按原倍率扣回

3. 成长值不受倍率影响
   - 始终 1 元 = +1 成长值
   - 避免高等级用户通过消费加速升级
```

### 4.3 积分有效期规则

```
1. 有效期标准
   青铜/白银：365 天
   黄金：     456 天（约 15 个月）
   铂金：     548 天（约 18 个月）
   钻石：     730 天（约 24 个月）

2. 升级时的有效期处理
   - 现有积分有效期延长至新等级标准
   - 只延长，不缩短（GREATEST 逻辑）
   - 新获得积分按新等级有效期计算

3. 过期提醒
   提前 30 天：站内信
   提前  7 天：站内信 + Push
   过期当天：账单通知
```

## 二、核心业务逻辑

### 2.1 商品列表查询逻辑

```
用户请求商城列表
  │
  ├─ 读取 user.level_id → 确定可见商品范围
  │   WHERE min_level_id <= user.level_id
  │
  ├─ 过滤上架状态
  │   WHERE status = 1
  │   AND (on_sale_at IS NULL OR on_sale_at <= NOW())
  │   AND (off_sale_at IS NULL OR off_sale_at > NOW())
  │
  ├─ 计算每个商品的实际兑换积分
  │   IF discount_enabled = 1:
  │     actual_cost = ceil(points_cost × mall_discount_pct / 100)
  │   ELSE:
  │     actual_cost = points_cost
  │
  ├─ 优先购标记
  │   IF priority_purchase = 1:
  │     IF user.level_id >= priority_level_id → 可立即兑换
  │     ELSE IF NOW() >= priority_open_at     → 可兑换
  │     ELSE                                  → 展示倒计时
  │
  └─ 返回列表（含实际积分、折扣标签、库存状态）
```

### 2.2 兑换流程

```
用户发起兑换请求
  │
  ├─ 【幂等校验】生成 idempotency_key（user_id + product_id + timestamp）
  │   防止网络重试导致重复兑换
  │
  ├─ 【前置校验】（快速失败，不加锁）
  │   ├─ 商品是否存在且上架
  │   ├─ 用户等级是否满足 min_level_id
  │   ├─ 用户积分是否充足（user.points >= actual_cost）
  │   ├─ 优先购时间窗口是否开放
  │   └─ 用户兑换次数是否超限
  │       SELECT COUNT(*) FROM mall_orders
  │       WHERE user_id=? AND product_id=?
  │       AND status NOT IN (4,6)  -- 排除取消和退款
  │       AND created_at >= period_start  -- 按周期类型计算起点
  │
  ├─ 【事务开始】
  │   │
  │   ├─ 锁库存（有限库存商品）
  │   │   SELECT remaining_stock FROM mall_products
  │   │   WHERE id = ? FOR UPDATE
  │   │   IF remaining_stock <= 0 → 抛出"库存不足"异常，回滚
  │   │
  │   ├─ 扣减库存
  │   │   UPDATE mall_products
  │   │   SET remaining_stock = remaining_stock - 1
  │   │   WHERE id = ? AND remaining_stock > 0
  │   │   IF affected_rows = 0 → 抛出"库存不足"异常，回滚
  │   │
  │   ├─ 写库存流水
  │   │   INSERT mall_stock_logs (type=1, change=-1)
  │   │
  │   ├─ 扣减用户积分（FIFO）
  │   │   调用积分扣减服务（见 2.3）
  │   │
  │   ├─ 创建兑换订单
  │   │   INSERT mall_orders
  │   │   product_snapshot = 当前商品JSON快照
  │   │   points_cost      = actual_cost（折扣后）
  │   │   original_cost    = points_cost（折扣前）
  │   │   discount_pct     = mall_discount_pct
  │   │
  │   └─ 虚拟商品立即发放
  │       IF type IN (2,3,4):
  │         发放券码/权益，UPDATE mall_orders SET status=3
  │       IF type = 1（实物）:
  │         status=1（待处理），等待运营发货
  │
  └─ 【事务提交】
      │
      └─ 异步处理
          ├─ 发送兑换成功通知
          ├─ 库存预警检查（remaining_stock <= stock_warn_line → 告警）
          └─ 更新商品状态（remaining_stock=0 → status=3 售罄）
```

### 2.3 积分扣减（FIFO）

```
目标：优先扣除最早获得、最快过期的积分

实现方案：

FUNCTION deduct_points(user_id, amount):

  -- Step 1: 校验总积分
  SELECT points FROM users WHERE id = user_id FOR UPDATE
  IF points < amount → 抛出"积分不足"异常

  -- Step 2: FIFO 查询待扣积分批次
  remaining = amount
  batches = SELECT id, points_remaining, expire_at
            FROM points_logs
            WHERE user_id = user_id
              AND status = 'active'
              AND points_remaining > 0
              AND (expire_at IS NULL OR expire_at > NOW())
            ORDER BY expire_at ASC NULLS LAST, id ASC
            FOR UPDATE

  -- Step 3: 逐批扣减
  deduct_records = []
  FOR batch IN batches:
    IF remaining <= 0: BREAK
    deduct = MIN(remaining, batch.points_remaining)
    deduct_records.append({id: batch.id, deduct: deduct})
    remaining -= deduct

  -- Step 4: 批量更新
  FOR record IN deduct_records:
    UPDATE points_logs
    SET points_remaining = points_remaining - record.deduct,
        status = IF(points_remaining - record.deduct = 0, 'used', 'active')
    WHERE id = record.id

  -- Step 5: 更新用户积分余额
  UPDATE users
  SET points = points - amount
  WHERE id = user_id

  -- Step 6: 写扣减日志
  INSERT points_logs (
    type           : 'mall_redeem',
    points         : -amount,
    growth_delta   : 0,
    ref_id         : order_id,
    related_batches: JSON(deduct_records)  -- 记录扣了哪些批次
  )
```

### 2.4 退款流程

```
触发场景：
├── 实物商品：用户申请退款（未发货）
├── 虚拟商品：原则上不退（券码已发放）
│   特殊情况：券码未使用且在有效期内，运营审核后可退
└── 系统异常：自动触发退款

退款流程：

运营/系统触发退款
  │
  ├─ 校验订单状态（只有特定状态可退款）
  │   实物：status IN (1,2) 可退
  │   虚拟：status = 3 且券码未使用 可退（需运营审核）
  │
  ├─ 【事务开始】
  │   │
  │   ├─ 回补积分
  │   │   INSERT points_logs (
  │   │     type          : 'mall_refund',
  │   │     points        : +original_points_cost,  -- 退回原始积分（不含折扣差）
  │   │     expire_at     : 原批次过期时间 或 NOW() + 用户当前等级有效期
  │   │   )
  │   │   UPDATE users SET points = points + amount
  │   │
  │   ├─ 回补库存（有限库存）
  │   │   UPDATE mall_products
  │   │   SET remaining_stock = remaining_stock + 1,
  │   │       status = IF(status=3, 1, status)  -- 售罄→重新上架
  │   │   INSERT mall_stock_logs (type=3, change=+1)
  │   │
  │   ├─ 作废券码（虚拟商品）
  │   │   调用券码作废接口
  │   │
  │   └─ 更新订单状态 → status=6（已退款）
  │
  └─ 【事务提交】
      └─ 发送退款成功通知
```

│ 重复提交            │ 幂等 key + 数据库唯一索引            │
│                    │ 前端按钮提交后置灰 3 秒              │
├──────────────────────────────────────────────────────────┤
│ 积分余额不一致       │ users.points 与 points_logs 定期对账│
│                    │ 每日凌晨跑对账任务，差异告警          │
├──────────────────────────────────────────────────────────┤
│ 券码泄露            │ 虚拟券码加密存储                    │
│                    │ 展示时实时解密，不缓存明文            │
├──────────────────────────────────────────────────────────┤
│ 恶意刷兑            │ 同一用户同一商品频率限制             │
│                    │ 异常行为触发人工审核                  │
├──────────────────────────────────────────────────────────┤
│ 等级折扣计算精度     │ 统一用 ceil()（向上取整）           │
│                    │ 避免出现 0 积分兑换的极端情况         │
└──────────────────────────────────────────────────────────┘
```

# 任务中心设计

## 前置：任务中心定位

```
任务中心的核心目标：
├── 引导用户完成关键行为路径（新手任务）
├── 维持用户日常活跃（日常任务）
├── 驱动用户完成高价值行为（成长任务）
└── 配合运营活动灵活发放奖励（活动任务）

与行为奖励矩阵的关系：
行为奖励矩阵 = 规则层（什么行为给什么奖励）
任务中心     = 展示层 + 进度追踪层（让用户看见目标和进度）
两者共用同一套积分/成长值发放服务
```

## 一、任务类型体系

### 1.1 四类任务总览

```
任务中心
├── 🌱 新手任务（一次性，引导核心路径）
├── 📅 日常任务（每日/每周重置，维持活跃）
├── 🏆 成长任务（里程碑式，永久记录）
└── 🎪 活动任务（运营配置，限时限量）
```

### 1.2 任务分类详细定义

| 维度     | 🌱 新手任务 | 📅 日常任务   | 🏆 成长任务 | 🎪 活动任务 |
| -------- | ----------- | ------------- | ----------- | ----------- |
| 触发对象 | 新注册用户  | 全体用户      | 全体用户    | 运营指定    |
| 完成次数 | 1次（永久） | 每日/每周重置 | 里程碑触发  | 活动期内    |
| 进度展示 | 步骤式      | 当日进度      | 累计进度    | 活动进度    |
| 过期机制 | 注册后30天  | 自然日/周     | 永不过期    | 活动结束    |
| 奖励类型 | 积分为主    | 积分为主      | 积分+成长值 | 运营配置    |
| 核心目的 | 功能引导    | 日活维持      | 长期留存    | 活动拉动    |

## 三、核心业务逻辑

### 3.1 事件驱动架构

```
所有用户行为 → 发布事件 → 任务中心订阅处理

事件总线设计：

用户完成某个行为
  │
  ├─ 业务服务处理主逻辑（下单、签到等）
  │
  └─ 发布领域事件（异步，不阻塞主流程）
      event = {
        event_code : 'order.completed',
        user_id    : 123,
        ref_type   : 'order',
        ref_id     : 456,
        metadata   : {
          amount        : 200.00,   // 订单金额
          is_first_order: false,    // 是否首单
          tool_code     : null      // 工具码（工具类事件）
        },
        occurred_at: '2024-01-15T10:30:00Z'
      }
      │
      └─ 任务中心消费事件 → 触发进度更新
```

### 3.2 事件码与任务映射

```
trigger_event 对照表：

事件码                  │ 触发场景           │ metadata 关键字段
────────────────────────┼────────────────────┼──────────────────
user.registered         │ 用户注册完成       │ -
user.profile_completed  │ 资料完善达标       │ -
user.signed_in          │ 每日签到           │ consecutive_days
order.completed         │ 订单完成           │ amount, is_first
invite.registered       │ 邀请好友注册       │ invitee_id
invite.first_consumed   │ 被邀请人首次消费   │ invitee_id, amount
feedback.submitted      │ 提交反馈           │ feedback_id
feedback.adopted        │ 反馈被采纳         │ feedback_id
content.shared          │ 分享内容           │ platform, content_id
tool.x.used             │ 使用 X 工具        │ tool_code
tool.any.used           │ 使用任意工具       │ tool_code
```

### 3.3 任务进度更新主流程

```
接收事件（event_code, user_id, metadata）
  │
  ├─ 查询匹配的任务模板
  │   SELECT * FROM task_templates
  │   WHERE trigger_event = event_code
  │     AND status = 1
  │     AND (valid_start IS NULL OR valid_start <= NOW())
  │     AND (valid_end IS NULL OR valid_end > NOW())
  │
  ├─ FOR EACH matched_task:
  │   │
  │   ├─ 【资格校验】
  │   │   ├─ 用户等级 >= min_level_id ？
  │   │   ├─ 新手任务：注册时间 <= onboarding_expire_days ？
  │   │   └─ 活动任务：用户是否在活动白名单？
  │   │
  │   ├─ 【获取/创建进度记录】
  │   │   period_start = calc_period_start(reset_type)
  │   │   progress = SELECT FROM user_task_progress
  │   │              WHERE user_id=? AND task_id=? AND period_start=?
  │   │   IF NOT EXISTS → INSERT 初始化记录
  │   │
  │   ├─ 【校验是否可继续】
  │   │   ├─ status = 3（已领取）且 reset_type = 0 → 跳过（永久完成）
  │   │   ├─ complete_times >= max_complete_times → 跳过
  │   │   └─ 今日 reward_times >= daily_limit → 跳过
  │   │
  │   ├─ 【计算进度增量】
  │   │   delta = calc_delta(progress_type, metadata)
  │   │   ┌─────────────────────────────────────────┐
  │   │   │ progress_type=1（单次）: delta = 1       │
  │   │   │ progress_type=2（累计次数）: delta = 1   │
  │   │   │ progress_type=3（累计金额）:             │
  │   │   │   delta = floor(metadata.amount)        │
  │   │   │ progress_type=4（连续天数）:             │
  │   │   │   delta = metadata.consecutive_days     │
  │   │   │   current_progress = delta（直接覆盖）   │
  │   │   └─────────────────────────────────────────┘
  │   │
  │   ├─ 【更新进度（乐观锁）】
  │   │   UPDATE user_task_progress
  │   │   SET current_progress = MIN(
  │   │         current_progress + delta,
  │   │         target_progress  -- 不超过目标值
  │   │       ),
  │   │       status = IF(
  │   │         current_progress + delta >= target_progress,
  │   │         2,  -- 已完成待领取
  │   │         1   -- 进行中
  │   │       ),
  │   │       updated_at = NOW()
  │   │   WHERE id = ? AND updated_at = last_updated_at  -- 乐观锁
  │   │   IF affected_rows = 0 → 重试（最多3次）
  │   │
  │   ├─ 【写完成日志】
  │   │   INSERT task_completion_logs
  │   │
  │   └─ 【触发奖励发放】
  │       IF is_completed = true → 调用奖励发放服务
  │
  └─ 处理完成
```

### 3.4 奖励发放服务

```
发放条件：
├── 自动发放（推荐）：任务完成后立即发放，无需用户手动领取
└── 手动领取：用户点击"领取"按钮触发（适合活动任务，增加仪式感）

自动发放流程：

任务完成（is_completed = true）
  │
  ├─ 【事务开始】
  │   │
  │   ├─ 发放积分
  │   │   INSERT points_logs (
  │   │     type         : 'task_reward',
  │   │     points       : +reward_points,
  │   │     growth_delta : +reward_growth,
  │   │     ref_type     : 'task',
  │   │     ref_id       : task_id,
  │   │     expire_at    : NOW() + user_level.points_validity_days
  │   │   )
  │   │   UPDATE users SET
  │   │     points       = points + reward_points,
  │   │     growth_value = growth_value + reward_growth,
  │   │     total_points = total_points + reward_points
  │   │
  │   ├─ 发放额外奖励（如有）
  │   │   IF reward_extra.type = 'coupon' → 发放优惠券
  │   │   IF reward_extra.type = 'mall_product' → 直接发放商城商品
  │   │
  │   ├─ 更新任务状态
  │   │   UPDATE user_task_progress SET
  │   │     status          = 3,  -- 已领取
  │   │     reward_times    = reward_times + 1,
  │   │     last_rewarded_at = NOW()
  │   │
  │   └─ 更新完成日志
  │       UPDATE task_completion_logs SET
  │         reward_issued    = 1,
  │         reward_issued_at = NOW()
  │
  ├─ 【事务提交】
  │
  ├─ 触发升级检测（growth_value 变化后）
  │
  └─ 推送奖励通知（异步）
      "🎉 任务完成！获得 XX 积分"
```

### 3.5 任务重置服务

```
触发方式：定时任务（Cron）

每日 00:00 执行：
  重置 reset_type = 1（每日任务）

每周一 00:00 执行：
  重置 reset_type = 2（每周任务）

每月1日 00:00 执行：
  重置 reset_type = 3（每月任务）

重置逻辑：

FOR EACH 需要重置的任务:
  -- 不删除旧记录，插入新周期记录
  INSERT user_task_progress (
    user_id         : user_id,
    task_id         : task_id,
    current_progress: 0,
    target_progress : task.progress_target,
    status          : 1,
    period_start    : new_period_start,
    complete_times  : 0
  )
  ON DUPLICATE KEY UPDATE ... -- 幂等处理

  -- 旧记录标记过期（status=4）
  UPDATE user_task_progress
  SET status = 4
  WHERE user_id = ? AND task_id = ?
    AND period_start < new_period_start
    AND status IN (1, 2)  -- 未完成的标记过期

注意：
├── 重置不影响 complete_times（历史完成次数保留在日志中）
├── 连续签到任务（progress_type=4）不走重置逻辑
│   由签到事件的 consecutive_days 直接覆盖进度
└── 分批处理，每批 500 条，避免锁表
```

### 3.6 新手任务过期处理

```
定时任务：每日 00:00 检查

SELECT utp.* FROM user_task_progress utp
JOIN task_templates tt ON utp.task_id = tt.id
JOIN users u ON utp.user_id = u.id
WHERE tt.category = 1  -- 新手任务
  AND utp.status IN (1, 2)  -- 未完成
  AND tt.onboarding_expire_days IS NOT NULL
  AND DATE_ADD(u.created_at, INTERVAL tt.onboarding_expire_days DAY) < NOW()

→ UPDATE status = 4（已过期）
→ 发送"新手任务即将过期"提醒（过期前3天）
```

## 五、特殊场景处理

### 5.1 连续签到任务的特殊逻辑

```
连续签到任务（progress_type=4）与普通累计任务不同：

普通累计：进度只增不减
连续签到：断签后进度归零，重新计算

实现方式：
├── 不依赖 current_progress 累加
├── 直接读取 metadata.consecutive_days（签到服务计算）
└── current_progress = consecutive_days（直接覆盖）

示例：
  用户连续签到 12 天 → current_progress = 12
  第 13 天断签 → consecutive_days 归零
  第 14 天重新签到 → consecutive_days = 1 → current_progress = 1

成长任务（连续30天）的完成判定：
  consecutive_days >= 30 → 触发完成
  完成后即使断签，任务状态保持"已完成"（成长任务不重置）
```

### 5.2 消费金额类任务的退款处理

```
场景：用户消费 320 元（成长任务进度 320/500）
      后退款 100 元，实际消费 220 元

处理方案：
├── 方案 A（推荐）：退款不回退任务进度
│   理由：任务进度是激励行为，不应因退款惩罚用户
│         且退款已扣回积分，不存在双重获利
│
└── 方案 B：退款回退进度
    风险：用户体验差，容易引发投诉
    实现复杂：需要追踪每笔订单对应的进度增量

结论：采用方案 A，退款只回退积分，不回退任务进度
在规则说明中注明："任务进度以消费行为触发时计算，退款不影响进度"
```

### 5.3 任务奖励补发机制

```
场景：系统异常导致任务完成但奖励未发放

检测方式：
  定时任务（每小时）扫描：
  SELECT * FROM task_completion_logs
  WHERE is_completed = 1
    AND reward_issued = 0
    AND created_at < NOW() - INTERVAL 5 MINUTE  -- 5分钟前完成但未发放

处理：
  重新触发奖励发放流程
  发放前检查 user_task_progress.reward_times 防止重复发放
  记录补发日志，供运营审计
```

# 积分过期完整流程设计

## 前置：过期机制核心原则

```
已确认规则：
├── 过期方式：FIFO（先进先出，优先过期最早获得的积分）
├── 过期周期：获得日起 365 天（滚动过期，非自然年）
├── 等级延长：黄金 456天 / 铂金 548天 / 钻石 730天
├── 成长值：永不过期
└── 过期积分：不可恢复

设计目标：
├── 准确：每一分积分的过期时间精确可追溯
├── 及时：过期前多次提醒，减少用户损失感
├── 可靠：过期执行不漏单、不重复
└── 透明：用户随时可查看即将过期的积分明细
```

## 二、过期执行流程

### 2.1 整体时序图

```
每日 00:00
  │
  ├─ T1: 过期执行任务（核心）
  │       扫描今日到期积分 → 执行过期 → 更新余额
  │
  ├─ T2: 提醒扫描任务
  │       扫描 30/7/1 天后到期的积分 → 生成提醒记录
  │
  ├─ T3: 提醒发送任务
  │       读取待发送提醒 → 调用通知服务发送
  │
  └─ T4: 日终对账任务（00:30，等T1完成后）
          生成每日快照 → 校验余额一致性 → 异常告警
```

### 2.2 过期执行任务（T1）

```
执行时间：每日 00:05（留5分钟等跨日事务完成）
执行方式：分批处理，每批 200 条

FUNCTION run_expiry_job(batch_date):

  batch_no = generate_batch_no()  // 如：EXP20240115001

  -- Step 1: 查询今日到期批次
  expiring_batches = SELECT
    pl.id,
    pl.user_id,
    pl.points_remaining,
    pl.expire_at
  FROM points_logs pl
  WHERE pl.status = 1                          -- 有效状态
    AND pl.points_remaining > 0                -- 有剩余积分
    AND pl.expire_at >= batch_date 00:00:00    -- 今日到期
    AND pl.expire_at <  batch_date 23:59:59
  ORDER BY pl.user_id, pl.expire_at ASC
  LIMIT 200                                    -- 分批

  IF COUNT(expiring_batches) = 0 → 结束

  -- Step 2: 按用户分组
  user_groups = GROUP BY user_id

  -- Step 3: 逐用户处理（事务）
  FOR EACH user_group:

    【事务开始】

    total_expired = SUM(batch.points_remaining)

    -- 3.1 批量更新积分批次状态
    UPDATE points_logs
    SET status          = 3,           -- 已过期
        points_remaining = 0,
        expired_at      = NOW()
    WHERE id IN (batch_ids)
      AND status = 1                   -- 防并发
      AND points_remaining > 0

    -- 3.2 扣减用户积分余额
    UPDATE users
    SET points = points - total_expired
    WHERE id = user_id
      AND points >= total_expired      -- 防止余额为负

    IF affected_rows = 0:
      -- 余额不足（异常情况），记录错误，跳过该用户
      LOG ERROR: '用户积分余额异常'
      ROLLBACK
      CONTINUE

    -- 3.3 写过期执行记录
    INSERT points_expiry_logs (
      user_id        : user_id,
      points_log_id  : batch_id,
      expired_points : batch.points_remaining,
      expire_at      : batch.expire_at,
      executed_at    : NOW(),
      batch_no       : batch_no,
      status         : 1
    ) FOR EACH batch

    -- 3.4 写积分流水（用户可见的明细）
    INSERT points_logs (
      user_id      : user_id,
      type         : 'expired',
      points       : -total_expired,
      growth_delta : 0,
      expire_at    : NULL,
      status       : 2,              -- 已用完（特殊标记，不参与FIFO）
      remark       : '积分已过期'
    )

    【事务提交】

  -- Step 4: 继续下一批（递归/循环直到处理完）
  IF has_more → run_expiry_job(batch_date, offset + 200)
```

### 2.3 失败重试机制

```
过期执行失败的处理：

失败场景：
├── 数据库超时
├── 用户余额异常（points < 应扣金额）
└── 死锁

重试策略：
  第1次失败 → 立即重试
  第2次失败 → 5分钟后重试
  第3次失败 → 30分钟后重试
  第3次仍失败 → 标记为人工处理，触发告警

UPDATE points_expiry_logs
SET status      = 2,           -- 失败
    retry_times = retry_times + 1,
    last_error  = error_message
WHERE id = ?

-- 补偿任务（每小时扫描失败记录）
SELECT * FROM points_expiry_logs
WHERE status = 2
  AND retry_times < 3
  AND created_at > NOW() - INTERVAL 24 HOUR
→ 重新触发过期流程
```

## 三、过期提醒流程

### 3.1 提醒扫描任务（T2）

```
执行时间：每日 00:10
目标：提前生成未来需要发送的提醒记录

FUNCTION scan_expiry_notices():

  notice_rules = [
    {type: 1, days_before: 30, channels: ['in_app']},
    {type: 2, days_before: 7,  channels: ['in_app', 'push']},
    {type: 3, days_before: 1,  channels: ['in_app', 'push']},
    {type: 4, days_before: 0,  channels: ['in_app']}
  ]

  FOR EACH rule IN notice_rules:

    target_date = TODAY + rule.days_before

    -- 查询该日期有积分到期的用户
    expiring_users = SELECT
      user_id,
      SUM(points_remaining) AS expiring_points,
      DATE(expire_at)       AS expire_date
    FROM points_logs
    WHERE status = 1
      AND points_remaining > 0
      AND DATE(expire_at) = target_date
    GROUP BY user_id, DATE(expire_at)
    HAVING expiring_points > 0

    FOR EACH user IN expiring_users:

      FOR EACH channel IN rule.channels:

        idempotency_key = MD5(
          user_id + '_' + rule.type + '_' +
          expire_date + '_' + channel
        )

        -- 幂等插入（已存在则跳过）
        INSERT IGNORE INTO points_expiry_notices (
          user_id         : user.user_id,
          notice_type     : rule.type,
          expiring_points : user.expiring_points,

### 3.2 提醒发送任务（T3）

```
执行时间：
├── 站内信：每日 00:15（低峰期，不打扰用户）
├── Push：  每日 10:00（用户活跃时段）
└── 短信：  每日 10:30（如有）

FUNCTION send_expiry_notices(channel):

  pending_notices = SELECT *
  FROM points_expiry_notices
  WHERE status = 1
    AND channel = channel
    AND expire_date >= TODAY  -- 过滤已过期的提醒
  ORDER BY notice_type ASC, expire_date ASC
  LIMIT 500

  FOR EACH notice IN pending_notices:

    -- 构建消息内容
    message = build_message(notice)

    -- 调用通知服务
    result = notification_service.send(
      user_id : notice.user_id,
      channel : channel,
      content : message
    )

    -- 更新发送状态
    UPDATE points_expiry_notices
    SET status     = IF(result.success, 2, 3),
        sent_at    = IF(result.success, NOW(), NULL),
        fail_reason = IF(result.success, NULL, result.error)
    WHERE id = notice.id
```

### 3.4 提醒发送规则

```

### 4.2 升级触发延长流程

```
用户升级（from_level → to_level）
  │
  ├─ 计算新有效期天数
  │   new_validity = to_level.points_validity_days
  │   old_validity = from_level.points_validity_days
  │
  ├─ 查询需要延长的积分批次
  │   SELECT id, expire_at FROM points_logs
  │   WHERE user_id = ?
  │     AND status = 1
  │     AND points_remaining > 0
  │     AND expire_at IS NOT NULL
  │     AND expire_at < NOW() + INTERVAL new_validity DAY
  │   -- 只处理"当前过期时间 < 新有效期"的批次
  │
  ├─ 批量更新过期时间
  │   UPDATE points_logs
  │   SET expire_at = GREATEST(
  │     expire_at,
  │     created_at + INTERVAL new_validity DAY
  │   )
  │   WHERE id IN (batch_ids)
  │
  ├─ 作废旧的过期提醒记录
  │   UPDATE points_expiry_notices
  │   SET status = 4  -- 已作废
  │   WHERE user_id = ?
  │     AND status = 1  -- 待发送
  │     AND expire_date < DATE(NOW() + INTERVAL new_validity DAY)
  │
  └─ 记录延长日志
      INSERT points_logs (
        type    : 'validity_extended',

## 五、对账与监控

### 5.1 日终对账任务（T4）

```
执行时间：每日 01:00（等过期任务完成后）

FUNCTION daily_reconciliation(date):

  -- Step 1: 生成每日快照
  INSERT INTO points_daily_snapshots
  SELECT
    date                              AS snapshot_date,
    u.id                              AS user_id,
    u.points                          AS points_balance,
    u.growth_value                    AS growth_value,
    COALESCE(earned.total, 0)         AS points_earned,
    COALESCE(spent.total, 0)          AS points_spent,
    COALESCE(expired.total, 0)        AS points_expired
  FROM users u
  LEFT JOIN (
    SELECT user_id, SUM(points) AS total
    FROM points_logs
    WHERE points > 0 AND DATE(created_at) = date
    GROUP BY user_id
  ) earned ON u.id = earned.user_id
  LEFT JOIN (
    SELECT user_id, ABS(SUM(points)) AS total
    FROM points_logs
    WHERE points < 0 AND type != 'expired'
      AND DATE(created_at) = date
    GROUP BY user_id
  ) spent ON u.id = spent.user_id
  LEFT JOIN (
    SELECT user_id, SUM(expired_points) AS total
    FROM points_expiry_logs
    WHERE DATE(executed_at) = date AND status = 1
    GROUP BY user_id
  ) expired ON u.id = expired.user_id
  ON DUPLICATE KEY UPDATE ...

  -- Step 2: 余额一致性校验
  -- 理论余额 = 昨日余额 + 今日获得 - 今日消耗 - 今日过期
  anomalies = SELECT
    today.user_id,
    yesterday.points_balance                          AS yesterday_balance,
    today.points_earned                               AS earned,
    today.points_spent                                AS spent,
    today.points_expired                              AS expired,
    (yesterday.points_balance
      + today.points_earned
      - today.points_spent
      - today.points_expired)                         AS expected_balance,
    today.points_balance                              AS actual_balance,
    (today.points_balance - expected_balance)         AS diff
  FROM points_daily_snapshots today
  LEFT JOIN points_daily_snapshots yesterday
    ON today.user_id = yesterday.user_id
    AND yesterday.snapshot_date = date - 1
  WHERE today.snapshot_date = date
    AND ABS(today.points_balance - expected_balance) > 0

  IF COUNT(anomalies) > 0:
    → 写入异常日志
    → 触发告警（邮件/钉钉）
    → 人工核查
```

# 接口设计文档

## 前置：接口规范

```
基础规范：
├── 协议：HTTPS
├── 风格：RESTful
├── 版本：/api/v1/
├── 认证：Bearer Token（JWT）
├── 编码：UTF-8
└── 格式：JSON

统一响应结构：
{
  "code":    0,          // 0=成功 非0=错误
  "message": "success",  // 错误时为错误描述
  "data":    {},         // 业务数据
  "ts":      1705286400  // 服务器时间戳
}

错误码规范：
├── 0      成功
├── 1001   未登录 / Token 失效
├── 1002   权限不足
├── 1003   参数错误
├── 2001   积分不足
├── 2002   等级不足
├── 2003   库存不足
├── 2004   超出兑换限制
├── 2005   商品已下架
├── 2006   活动已结束
└── 5000   服务器内部错误
```

## 八、性能与安全规范

### 8.1 缓存策略

```
接口                    缓存策略              TTL
─────────────────────────────────────────────────────
GET /member/home        用户维度缓存          60 秒
GET /member/level       用户维度缓存          300 秒
GET /points/overview    用户维度缓存          30 秒
GET /points/logs        不缓存（实时性要求高）  -
GET /points/expiring    用户维度缓存          300 秒
GET /tasks              用户维度缓存          30 秒
GET /mall/home          全局缓存             300 秒
GET /mall/products      全局缓存             60 秒
GET /mall/products/{id} 全局缓存             60 秒
GET /mall/orders        不缓存               -

缓存失效触发：
├── 积分变动 → 清除 points/* 缓存
├── 等级变动 → 清除 member/* 缓存
├── 任务完成 → 清除 tasks 缓存
└── 商品变更 → 清除 mall/products/* 缓存
```

### 8.2 限流规范

```
接口限流规则（per user）：

POST /member/signin      1次/天（业务限制）
POST /tasks/{id}/claim   10次/分钟
POST /mall/orders        5次/分钟
GET  /*                  100次/分钟

全局限流（per IP）：
所有接口：200次/分钟

触发限流响应：
HTTP 429 Too Many Requests
{
  "code":       429,
  "message":    "请求过于频繁，请稍后再试",
  "retry_after": 60   // 秒
}
```

### 8.3 安全规范

```
幂等性保障：
├── POST 接口必须支持 Idempotency-Key
├── Key 格式：客户端生成的 UUID v4
├── 服务端缓存 Key 24 小时
└── 相同 Key 的重复请求返回首次结果

敏感数据处理：
├── 虚拟券码：响应中加密，前端展示时解密
├── 手机号：列表接口脱敏（138****0000）
└── 收货地址：仅订单详情接口返回完整信息

接口鉴权：
├── 所有接口需要 Bearer Token
├── Token 过期时间：7 天
├── 刷新 Token：无感刷新
└── 异地登录：强制重新登录
```

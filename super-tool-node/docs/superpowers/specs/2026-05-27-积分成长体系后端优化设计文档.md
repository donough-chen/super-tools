## §1 背景与目标

### 1.1 背景

[2026-04-10 会员等级体系设计文档](../specs/2026-04-10-会员等级体系设计文档.md) 与 [2026-05-26 MVP v2 实施计划](../plans/2026-05-26-积分成长体系MVP实施计划-v2.md) 已落地了 5 等级 / FIFO 积分批次 / 升级延长有效期 / 任务中心 / 积分商城 / 对账双层 / 过期提醒等模块。但在最新的 [深度评估报告](../../analysis/积分与成长体系深度评估报告.md) 与现网代码的双向比对中，发现 **30+ 项偏差**，覆盖：

- 数据完整性（balance UNSIGNED 与负值语义冲突）
- 数值锚点漂移（评估报告 vs MVP v2 vs 现网种子）
- 流程缺口（注册 / 退款事件未派发）
- 工程隐患（admin 写接口缺白名单 / GREATEST 用 SQL 字面量拼接）
- 体验细节（过期通知缺金额 / sign 月日历缺奖励预览）

### 1.2 目标

一次性收敛上述全部偏差，使后端达到"评估报告 + MVP v2"双重要求的对齐状态，为后续 admin / H5 的对接提供稳定 contract。

### 1.3 范围内（In Scope）

1. 14 个后端文件的代码级修复（detail 见 §2/§4/§5）
2. 1 条新增 SQL 迁移：`database/026_points_growth_system_optimization.sql`
3. 2 处业务事件埋点补齐：`register` / `refund_completed`
4. 1 个一次性历史用户迁移脚本：`scripts/migrate_existing_users_points.ts`
5. 单测 / 集成测试覆盖

### 1.4 范围外（Out of Scope）

- 管理端页面（`super-tools-admin`）
- H5 页面（`super-tools-web/packages/h5/micro-tools`）
- 积分体系 v3 路线项（季节活动 / 徽章 / 家族体系 / 跨链 NFT 等）
- 业务侧逻辑改造（`order/refund/feedback/auth/favorite/tool` 仅在指定行补 `event.emit()`，其他业务流不改）

### 1.5 关键决策（已敲定）

## §2 偏差清单（核心）

> **注**：经过对真实代码的二次核对，原 30 项中有若干"已修复"或"判断过悲观"，故重新组织为下表共 **34 项**。每项给出"问题 → 修复方案 → 影响文件 → 验收点"。

### 2.1 数据库（5 项）

#### **#1** [P0] `points_logs.balance` UNSIGNED 与"退款负余额"语义冲突

- **问题**：`025_full.sql` 把 `balance` 设为 `INT UNSIGNED`，而评估报告 §5.2 / MVP v2 §Task 4 明确"退款允许负余额"。当前 `member.refundPoints` 用 `Math.max(0, newBalance)` 钳零规避，导致流水中的 balance 永远 ≥ 0，对账时"理论值"和"实际值"产生系统性偏差，每个退款用户都触发误报警。
- **修复**：`ALTER TABLE points_logs MODIFY COLUMN balance INT NOT NULL DEFAULT 0`（INT 默认 SIGNED）
- **影响文件**：`database/026_optimization.sql`（新增）；同步移除 `member.ts:507` / `member.ts:271` 的 `Math.max(0, …)` 钳零逻辑（仅保留 `user_members.points` 的钳零）
- **验收**：退款后查询 `points_logs.balance` 能查到负值；`pointsReconcile.hourlyBalanceCheck` 不再对单纯退款用户报警

#### **#2** [P0] `user_members.points` UNSIGNED 同上

- **问题**：与 #1 同根；当前 `member.refundPoints` 已显式承认了"理论余额含负值，实际钳到 0"的设计。MVP v2 设计目标是"理论=实际"统一，需要 user_members 也支持负值才能彻底闭环。
- **修复**：`ALTER TABLE user_members MODIFY COLUMN points INT NOT NULL DEFAULT 0`
- **影响文件**：同上；`member.refundPoints` 改为直接 `member.points - refundAmount`，去掉钳零；`processExpiredBatches` 的 `Math.max(0, member.points - b.pointsRemaining)` 同步去钳零
- **验收**：退款后 `user_members.points` 可以为负，且与 `SUM(points_logs.points)` 完全一致

#### **#3** [P1] 等级 `points_expire_days` 数值笔误

- **问题**：`025_full.sql:338` 黄金等级（gold）的 `points_expire_days=456`。这显然是笔误（评估报告 §4.4 / MVP v2 都未提到 456 这个值；上下文是 free=365 / silver=365 / gold=? / diamond=730 / black=730）。MVP v2 §Decisions 明确 5 档为 "365/365/540/730/730" 或合理递增。
- **修复**：纠正为 `540`（介于 silver 365 与 diamond 730 中间，且评估报告"白金 540 天"语义吻合）
- **影响文件**：`database/026_optimization.sql` UPDATE
- **验收**：`SELECT JSON_EXTRACT(benefits, '$.points_expire_days') FROM member_levels WHERE code='gold'` = 540

#### **#4** [P1] 任务种子覆盖度不足

- **问题**：现网种子（025_full.sql 假定的 INSERT 部分）覆盖了基础 daily/newbie/achievement，但**未含**评估报告 §3 行为矩阵的下列任务：
  - `consume_milestone_500/1000/3000`（消费里程碑 3 档）
  - `subscribe_renewal`（订阅续费奖励，事件 payment.ts:238 已在 emit）
  - `year_active`（年度活跃，progressType=1，cycle=yearly）
  - `feedback_adopted_extra`（反馈被采纳的额外奖励层）
- **修复**：在 026 中 `INSERT IGNORE INTO tasks` 6 条种子（code 唯一索引保幂等）
- **影响文件**：`database/026_optimization.sql`
- **验收**：触发对应事件后 `user_tasks` 出现新行；管理端能查到 6 条新任务

#### **#5** [P1] `daily_cap_group=invite` 类型未实装上限

- **问题**：评估报告 §3 明确"邀请类奖励单日 ≤ 5 次"，025_full.sql 已建 `daily_cap_group` 字段，但 `task.ts:claim` 中只处理了 `task` 类，没处理 `invite` 类。
- **修复**：`task.ts:claim` 中扩展上限校验，新增 `invite` 分支，从 `system_configs` 读 `daily_cap_invite=5`（兜底 5）
- **影响文件**：`app/service/task.ts`；`database/026_optimization.sql` 补 `system_configs` 默认值
- **验收**：单元测试模拟用户当日 5 次邀请奖励触发后，第 6 次拒绝

### 2.2 签到（3 项）

#### **#6** [P2] sign 月日历缺奖励预览

- **问题**：H5 的"连签里程碑奖励"页面需要展示"7 天奖励 / 30 天奖励 / 365 天奖励"，但 `getSignStatus` 只返回 `signedDates / currentStreak / totalSignDays / todaySigned`，没有里程碑配置。
- **修复**：`getSignStatus` 返回中追加 `milestones: [{streak: 7, points: X}, ...]`，从 `tasks WHERE trigger_event='sign_streak'` 聚合
- **影响文件**：`app/service/sign.ts`
- **验收**：接口返回中包含 milestones 数组

#### **#7** [P1] sign 不写 `growth_earned`（连签 30/365 天的成长值）

- **问题**：MVP v2 §Task 6 设计了"连续 30/365 天签到额外给成长值"。当前 `sign.ts:80` 一律写 `growthEarned: 0`。里程碑成长值依赖 `sign_streak` 事件触发的任务奖励派发，逻辑上是 OK 的，但 `user_signs.growthEarned` 字段语义错位（设计文档预期用作"该次签到带来的成长值"，包含里程碑）。
- **修复**：保持 `user_signs.growthEarned=0`（每日签到底分确不带成长值，与设计一致）；改为在文档与字段注释中明确"`growth_earned` 仅记录每日签到底分对应的成长值（恒为 0），里程碑成长值由 task_completion_logs 单独记录"
- **影响文件**：`app/service/sign.ts` 注释更新；`app/model/user_sign.ts` 字段注释更新
- **验收**：注释清晰说明 0 的来源；不需要改逻辑（原始判断有误）

#### **#8** [P2] 日期换算未隔离 server / DB 时区

- **问题**：`sign.ts:todayStr()` 使用 `new Date()`（server 本地时区），而 DB 默认按 server 时区存。如果 server 部署在 UTC 而业务面向 +08:00，会导致"用户实际 23:30 签到却存为下一天"的错位。
- **修复**：所有 `todayStr` / `prevDayStr` 强制使用 `Asia/Shanghai`：
  ```ts
  new Date(new Date().toLocaleString('en-US', { timeZone: 'Asia/Shanghai' }));
  ```
- **影响文件**：`app/service/sign.ts`、`app/service/task.ts`（`localTodayStr`）、`app/service/pointsExpire.ts`（`localTodayStr`）、`app/service/pointsReconcile.ts`（`localTodayStr`）— 提取公共工具到 `app/lib/dateUtil.ts`
- **验收**：单元测试模拟 server 在 UTC 的情况下，业务日期仍按 +08:00 计算

### 2.4 事件（3 项）

#### **#14** [P1] 事件清单与实际 emit 字符串不一致

- **问题**：`event.ts:9` 注释列出的事件清单包含 `first_subscribe / invite_first_pay`，但 `payment.ts:238` 实际 emit `subscribe_renewal`（不在清单中），且 `invite_first_pay` 注释列出但未在任何业务方 emit。需要统一事件清单。
- **修复**：
  - 更新 `event.ts` 注释清单为真实出现的事件（删 invite_first_pay，加 subscribe_renewal、refund_completed、register）
  - 提取常量 `app/lib/eventCodes.ts`，业务方 import 使用
- **影响文件**：`app/service/event.ts`、新增 `app/lib/eventCodes.ts`、所有 emit 调用方改用常量
- **验收**：grep `event.emit('` 确保都使用常量

#### **#15** [P1] 跨 worker 广播仍有竞态

- **问题**：`event.ts:48` 用 `messenger.sendToApp` 广播，但**没有人订阅**！grep `messenger.on('domain-event'` 0 命中。这意味着多 worker 部署时，事件只在 emit 所在的 worker 同步派发到 TaskService，其他 worker 完全收不到。但因为 TaskService.onEvent 是用唯一索引幂等的，单 worker 派发就够用，不会丢事件（只是没能"分担"任务负载）。如果未来加分布式订阅方（缓存预热 / 通知扇出），会出问题。
- **修复**：在 `app/io.ts` 或 `app/agent.ts` 中订阅 messenger 'domain-event'，路由到 TaskService.onEvent。**注意幂等**：当 emit 所在 worker 已经派发过一次时，跨 worker 收到后应只走"补偿性派发"（DB 唯一索引会拒绝重复，相当于无操作）。
- **影响文件**：新增 `app/io.ts`（或在 `agent.ts` 中加监听）；`app/service/event.ts` 增 `dispatchFromMessenger` 方法
- **验收**：模拟 worker A emit 后 worker B 收到 'domain-event' 时调用 onEvent；DB 状态不重复

#### **#16** [P2] 没有事件落库追溯表

- **问题**：MVP v2 §Task 5 提到"通过 DB 落地实现最终一致"，但实际没建表。当前事件丢失只能靠 stderr 日志排查，且不能"重放"。
- **修复**：026 中新建 `domain_events` 表（id / event_code / user_id / payload / status / retry_count / created_at），event.emit 同时写一行 status='emitted'。后续如需重放，可扫描 `status='emitted'` 且 `created_at > X` 的行调 onEvent。
- **影响文件**：`database/026_optimization.sql`、新增 `app/model/domain_event.ts`、`app/service/event.ts:emit` 增写库逻辑
- **验收**：每次 emit 在 domain_events 多一行；模拟订阅方异常后能从表中重放

### 2.7 积分商城（4 项）

#### **#21** [P1] 商城退款 FIFO 反向回写优化

- **问题**：`member.refundPoints` 当前只回写"原批次"一个 logId 的 `points_remaining`。如果原批次的余额已被其他消费扣完（pointsRemaining=0），剩余的退款额度会全部走"扣会员余额"路径（在 X 修复后会变成实质负余额）。这在数学上是守恒的，但用户视角下"我兑换时扣了 100 分，退款时应拿回 100 分到我的可用余额"会产生预期偏差（拿回的部分变成"理论余额"而非"实际可用余额"）。
- **修复**：扩展 `refundPoints` 支持"反向 FIFO"：
  1. 优先回写原批次 points_remaining
  2. 若原批次剩余不够，按"消费方向"找最近的已消费批次（status=2 的同一用户的 logs，按 id DESC），把它们 status 改回 1，points_remaining 反向恢复
  3. 仍不够才扣会员余额
- **复杂度**：中（涉及反查 type=2 的负流水链路）
- **影响文件**：`app/service/member.ts:refundPoints`
- **验收**：单元测试 - 用户消费 100 后又赚 50，退 80 时：
  - 80 中先恢复消费批次 100→已消费的部分（恢复 80）
  - 用户 实际可用余额 += 80（而不是 50 + 30=80 的 "30 是负余额"）
- **降级方案**：如复杂度过高，加 feature flag `mall.refund.reverse_fifo`，默认 false（保持原逻辑），灰度后再开

### 3.3 关键风险

- **ALTER points_logs MODIFY balance**：MySQL 8 INT 同尺寸 unsigned→signed 是 INSTANT 操作（不锁表、瞬时完成）；MySQL 5.7 是 INPLACE（在线、可读写）。生产前必须确认 MySQL 版本 ≥ 8.0 或 5.7.32+
- **数据校验 SQL（执行 ALTER 前先跑）**：
  ```sql
  SELECT MAX(balance) FROM points_logs;       -- 确认 < 2147483647（INT signed max）
  SELECT MAX(points)  FROM user_members;
  ```
  若值接近上限，使用 BIGINT 而非 INT

| task                | claim 触发奖励入账        | 过期任务 claim 拒绝、超日上限拒绝 |
| event               | emit 后 onEvent 调用      | 跨 worker 重复触发的幂等          |
| pointsRule          | rule 缓存 5min            | invalidateCache 后立即生效        |
| pointsExpire        | extendOnUpgrade 取大值    | 升级后 expire_at 不缩短           |
| pointsMall          | 兑换 → 履约               | 退款反向 FIFO（核心）             |
| pointsReconcile     | 抽样命中 anomaly → alert  | 0 用户场景不报错                  |
| member.refundPoints | 反向 FIFO 链路            | 全链消费完场景的反向恢复          |
| idempotency         | enforce=true 无 key → 400 | 重复 key 返回首次响应             |

### 7.2 集成测试（3 条全链路）

1. **签到链路**：签到 → user_signs / user_members 更新 → sign_streak 事件 → 任务进度推进 → claim → points_logs / completion_log
2. **消费链路**：下单 → 完单 → first_consume + consume_milestone 事件 → 任务完成 → 升级 → extendExpireOnUpgrade
3. **兑换 / 退款链路**：兑换实物 → 库存 -1 → 等待发货 → 管理员退款 → 反向 FIFO 恢复 → 库存 +1 → refund_completed 事件

## §8 风险与上线策略

### 8.1 P0 风险

- **balance / points 改 SIGNED**：单一 ALTER 操作，瞬时完成；但生产前需确认 MySQL 版本（见 §3.3）；备份 + DBA 工单
- **反向 FIFO**：算法复杂度高，必须有 feature flag `mall.refund.reverse_fifo`，默认关；上线 1 周后开启，再 1 周观察后正式生效

### 8.2 灰度顺序

```
阶段 1（D+0）: 026 SQL + 后端代码部署，feature flag 全部关闭
阶段 2（D+1）: 历史用户迁移
阶段 3（D+3）: 开 reverse_fifo flag（仅商城退款新订单）
阶段 4（D+7）: 移除 feature flag（默认行为）
```

### 8.3 监控指标

- `pointsReconcile.hourlyBalanceCheck` 异常用户数（应 ≤ 个位数）
- `domain_events.status='emitted'` 滞留量（应近 0）
- `task_completion_logs.status='pending'` 滞留量（task_reward_resend 兜底，应 ≤ 100）
- 退款反向 FIFO 失败次数（应为 0）

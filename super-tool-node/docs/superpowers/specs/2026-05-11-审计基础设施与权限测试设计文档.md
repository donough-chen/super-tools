# 审计基础设施与权限测试设计文档（Spec-A1）

> **版本**: 1.0  |  **创建时间**: 2026-05-11  |  **作者**: brainstorming session
> **状态**: 待评审 → 实施计划
> **前置依赖**: Spec-B（管理端 RBAC 基础设施）已完成并合并 master
> **后续衔接**: Spec-A2（反馈与数据统计）、Spec-C（管理端 9 个业务页）

## 一、背景与目标

### 1.1 背景

Spec-B 已建立管理端 RBAC 基础设施（菜单/权限码/路由级权限组件）。但 RBAC 体系下还有两块**关键基础设施缺口**：

1. **审计追踪缺失**：现有 admin 接口（role / permission / tool / user / member）的写操作**没有任何留痕**，违反「重要业务变更必须可追溯」的合规与运维要求。`audit_logs` 表已在 init.sql 完整定义但**从未被使用**。
2. **权限调试工具缺失**：管理员排查"用户报错点不动按钮 / 角色配置是否符合预期"时，**只能靠人工对照 DB 表**，效率极低且容易判断失误。`system:permission-test:run` 权限码已在 006 SQL 预埋但**对应接口不存在**。

### 1.2 整体 Spec-A 拆分

按 brainstorming 决策，Spec-A 拆为 2 个独立 spec：

| Spec | 内容 | 状态 |
|---|---|---|
| **A1（本文档）** | 审计基础设施 + 权限测试工具 + 6 类高敏感写操作回填 | 设计中 |
| **A2** | 反馈管理（含 C 端提交） + 数据统计（含 5 个聚合接口） | 待 A1 完成 |

理由：A1 是 A2 / Spec-C 共同依赖的「框架/基础」层，先做 A1 可让 A2 controller 写操作直接复用 audit.log；Spec-C 的"审计日志页 + 权限测试页"也直接消费 A1 的接口。

### 1.3 目标

完成本 Spec-A1 后，达成：

1. ✅ 全栈审计能力：`service.audit.log()` + `audit_logs` 表写入 + 4 个查询接口（list/detail/export）
2. ✅ 6 类高敏感写操作（17 个接口）已挂审计调用，审计日志页有真实数据可展示
3. ✅ 权限调试工具：1 个接口 3 种 mode（user-overview / user-check / role-check）
4. ✅ 测试覆盖：~12 个核心 case
5. ✅ 文档：admin/audit-log + permission-test 接口文档完备

| `controller/admin/{role,tool,user,member}.ts` | 在 17 个高敏感方法内显式调用 audit.log | 路由不变 | service/audit |

### 3.4 关键不变量（实施阶段硬约束）

1. **`service.audit.log` 内部必须 try/catch + logger.warn**：审计写入失败永不影响主业务
2. **回填的 audit 调用必须放在 try/catch 双路径**：成功（try 末尾）+ 失败（catch 重抛之前）
3. **before 数据查询失败不阻塞主流程**：用 try/catch 包住 before 查询，失败时 `beforeData = null`
4. **permission-test 不挂 audit**：GET 操作，按 Q3 决策不审计
5. **password / token / secret 字段永不进 audit**：`_sanitizeParams` 兜底 + reset-password 显式不传 beforeData/afterData

### 4.2 service/audit.ts 完整契约

```typescript
import { Service } from 'egg';
import { Op } from 'sequelize';

export interface AuditLogPayload {
  module: string;
  action: string;
  description?: string;
  bizType?: string;
  bizId?: string | number;
  beforeData?: any;
  afterData?: any;
  status?: 0 | 1;          // 默认 1
  failReason?: string;
  override?: Partial<AuditLogAttributes>;
}

export interface AuditLogQuery {
  page?: number; pageSize?: number;
  startTime?: string; endTime?: string;
  userId?: number; module?: string; action?: string;
  status?: 0 | 1; keyword?: string;
}

export default class AuditService extends Service {
  /**
   * 写入一条审计日志
   * - 自动从 ctx 注入 user/ip/url/cost/trace 等
   * - 异常吞掉 + logger.warn（永不影响主业务）
   */
  async log(payload: AuditLogPayload): Promise<void> {
    try {
      const { ctx } = this;
      const user = (ctx.state as any).user;
      const startTime = (ctx.state as any).requestStartTime as number | undefined;

      await ctx.model.AuditLog.create({
        traceId: (ctx as any).tracer?.traceId || ctx.get('x-trace-id') || null,
        userId: user?.id ?? null,
        username: user?.username ?? null,
        platform: ctx.get('x-platform') || 'admin',
        module: payload.module,
        action: payload.action,
        description: payload.description ?? null,
        bizType: payload.bizType ?? null,
        bizId: payload.bizId != null ? String(payload.bizId) : null,
        beforeData: payload.beforeData ?? null,
        afterData: payload.afterData ?? null,
        ip: ctx.ip,
        userAgent: ctx.get('user-agent') || null,
        requestUrl: ctx.url,
        requestMethod: ctx.method,
        requestParams: this._sanitizeParams(ctx.request.body),
        responseCode: ctx.status || null,
        costTime: startTime ? Date.now() - startTime : null,
        status: payload.status ?? 1,
        failReason: payload.failReason ?? null,
        ...(payload.override || {}),
      });
    } catch (err) {
      this.ctx.logger.warn('[audit] log failed: %s', (err as Error).message);
    }
  }

  /** 列表查询（7 维过滤 + 分页；列表不含 before/after 减少响应大小） */
  async list(q: AuditLogQuery) { /* 见正文 */ }

  /** 单条详情（含完整 JSON） */
  async detail(id: number) { return this.ctx.model.AuditLog.findByPk(id); }

  /** 流式 CSV 导出，max ≤ 10000；超过截断且 set X-Audit-Truncated:true */
  async exportCsv(q: AuditLogQuery, max = 10000): Promise<void> { /* 见 4.4 */ }

  /** 请求参数脱敏 */
  private _sanitizeParams(body: any): any { /* 见 4.5 */ }
}
```

### 4.3 list 实现要点

- where 构造按 7 维过滤参数，全部命中已有索引（`idx_user_id` / `idx_module` / `idx_created_at`）
- 列表响应 `attributes: { exclude: ['beforeData','afterData','requestParams'] }` —— 避免 1MB 级别的 JSON 拖累分页
- 排序：`order: [['id', 'DESC']]`（id 自增等价 created_at 降序，但用 PK 更高效）
- 默认 pageSize=20，max=100

### 4.4 CSV 流式导出

要点：
- 使用 `PassThrough` Stream 作为 ctx.body
- UTF-8 BOM 开头：`\uFEFF`
- 中文表头：`ID,时间,用户,模块,动作,业务类型,业务ID,描述,IP,URL,方法,耗时(ms),状态,失败原因`
- 分批查询（每批 500，offset 累加）避免内存峰值
- 超过 max 后停止（不报错）+ Header `X-Audit-Truncated: true`
- 自实现 `_rowToCsv` + `csvField`（13 行）处理逗号 / 引号 / 换行转义
- **不引入 csv-stringify 依赖**

## 五、Permission Test Service 详细设计

### 5.1 三个 mode 的输入输出契约

#### Mode 1: `user-overview` — 用户全景

**Input**: `{ mode:'user-overview', userId }`

**Output**:
```jsonc
{
  "user": { "id": 123, "username": "alice", "nickname": "Alice", "status": 1 },
  "roles": [ { "id": 2, "code": "operator", "name": "运营管理员" } ],
  "isSuperAdmin": false,
  "permissionCodes": ["dashboard","tool","tool:menu","tool:list", ...],
  "menus": [ /* MenuNode[]，复用 getMenusForUser */ ],
  "stats": {
    "totalCodes": 42,
    "totalMenus": 6,
    "byModule": { "tool": 8, "category": 4, ... }
  }
}
```

#### Mode 2: `user-check` — 单接口/权限码命中检查

**Input**:
- 形态 A：`{ mode:'user-check', userId, code }`
- 形态 B：`{ mode:'user-check', userId, path, method }`

**Output**:
```jsonc
{
  "user": { "id": 123, "username": "alice" },
  "target": {
    "type": "code" | "api",
    "code": "tool:create",
    "path": "/api/admin/tools",
    "method": "POST",
    "permissionExists": true,
    "permissionId": 56,
    "permissionName": "创建工具"
  },
  "allowed": true,
  "matchedRoles": [ { "id": 1, "code": "admin", "name": "管理员" } ],
  "matchedPermissions": [ { "id": 56, "code": "tool:create", "via": "role:admin" } ],
  "denyReason": null
}
```

**denyReason 枚举**：

| 取值 | 触发条件 |
|---|---|
| `permission_not_exists` | code/api 在 permissions 表不存在 |
| `user_not_found` | userId 对应用户不存在 |
| `user_disabled` | 用户 status≠1 |
| `no_roles` | 用户未绑定任何角色 |
| `roles_disabled` | 所有角色 status≠1 |
| `permission_not_granted` | 角色未授予该权限码 |
| `permission_disabled` | 权限码 status≠1 |

> super_admin 短路：直接 `allowed=true`, `matchedRoles=[{code:'super_admin'}]`, `matchedPermissions=[{via:'super_admin_short_circuit'}]`

#### Mode 3: `role-check` — 角色权限矩阵

**Input**: `{ mode:'role-check', roleCode | roleId }`

**Output**:
```jsonc
{
  "role": { "id": 2, "code": "operator", "name": "运营管理员", "status": 1 },
  "ownedCodes": [ /* 全量 codes */ ],
  "permissionTree": [ /* 仅含 owned 节点的树 */ ],
  "stats": {
    "total": 42,
    "byModule": { "tool": 8, "category": 4, ... },
    "byType": { "menu": 12, "api": 30 }
  },
  "boundUserCount": 7
}
```

### 5.2 Service 方法签名


### 5.3 checkUserAccess 实现要点（顺序敏感的短路求值）

```
1. 查 user → user_not_found
2. user.status === 1 → user_disabled
3. 查 user_roles → no_roles
4. 至少一个角色 status=1 → roles_disabled
5. super_admin 短路 → allowed=true（不再继续）
6. 解析 target：
   - 形态 A: code 直接用
   - 形态 B: SELECT FROM permissions
            WHERE path=? AND method=? AND platform='admin' LIMIT 1
            找不到 → permission_not_exists
7. 权限码 status === 1 → permission_disabled
8. user codes ∋ code → allowed=true
   否则 → permission_not_granted
9. allowed=true 时回填 matchedRoles + matchedPermissions
   SQL: SELECT r.* FROM roles r
        JOIN role_permissions rp ON r.id=rp.role_id
        JOIN permissions p ON p.id=rp.permission_id
        JOIN user_roles ur ON ur.role_id=r.id
        WHERE ur.user_id=? AND p.code=? AND r.status=1 AND p.status=1
```

### 5.4 路径占位符的兜底处理

permissions 表中实际写入的 path 是带占位符（如 `/api/admin/tools/:id`），所以 user-check 形态 B 查询时**严格相等匹配即可命中**——这是已有 RBAC 中间件的检查方式。

唯一可能模糊匹配的场景：用户输入"实参 URL"如 `/api/admin/tools/5` 试图反查。本 spec **不支持**这种"实参 → 模板"的反向解析（这是 path-to-regexp 的反操作，通常不可逆），如有需要可在前端做"取消最后一段路径"的辅助 UI。

```typescript
async adjustPoints() {
  const userId = Number(this.ctx.params.id);
  const { delta, reason } = this.ctx.request.body;
  let before: any = null;
  try { before = await this.service.member.getPoints(userId); } catch {}

  try {
    const after = await this.service.member.adjustPoints(userId, delta, reason);
    await this.service.audit.log({
      module: 'member', action: 'adjust_points',
      bizType: 'member', bizId: userId,
      beforeData: { points: before }, afterData: { points: after, delta, reason },
      description: `调整用户 #${userId} 积分 ${delta > 0 ? '+' : ''}${delta}（${reason || '无原因'}）`,
      status: 1,
    });
    this.success({ points: after });
  } catch (e: any) {
    await this.service.audit.log({
      module: 'member', action: 'adjust_points',
      bizType: 'member', bizId: userId,
      beforeData: { points: before },
      description: `尝试调整积分 ${delta}`,
      status: 0, failReason: e.message,
    });
    throw e;
  }
}
```

### 7.4 回填的不变量（实施阶段硬约束）

1. **不重写业务逻辑**：仅在 controller 方法首尾加 before 查询 + try/catch + audit.log 调用
2. **不动 service 层**：所有 audit 调用都在 controller，service 保持纯净
3. **password / token / secret 字段不能进 beforeData/afterData**：调用方手动剔除 + service.audit 兜底脱敏
4. **bizId 强制 string**：service.audit 内部 `String(bizId)` 转换，避免 BIGINT JSON 精度问题
5. **action 词表硬约束**：英文小写下划线，固定枚举 `create / update / delete / batch_update / reset_password / adjust_points / export / login / logout`，禁止临时新词

## 九、风险与开放问题

### 9.1 风险（R1-R5）

| ID | 风险 | 缓解 |
|---|---|---|
| **R1** | 17 个回填接口涉及多 controller，引入回归 | 每 task ≤7 接口；每 task 跑 `test:auth` + 手工冒烟 |
| **R2** | audit_logs 持续增长 → 慢查询 | 已有 4 个索引；查询永远带 startTime；归档机制 future task |
| **R3** | password 漏到 audit | _sanitizeParams 兜底 + reset-password 模板规定不传 before/after |
| **R4** | requestStartTime middleware 漏挂 → costTime 全 null | 手工验收 #1 立即发现 |
| **R5** | mode typo（如 `usercheck`）静默失败 | controller 422 抛 `unknown mode: xxx` |

### 9.2 开放问题（plan 阶段决定）

| ID | 问题 | 待决 |
|---|---|---|
| **O1** | _sanitizeParams 兜底脱敏 vs controller 显式脱敏 | 双重保险：service 层兜底（必做） + controller 层显式删字段（推荐） |
| **O2** | bizId 多 ID 拼接（如 batch_update 的 ids.join(',')）超过 64 字节怎么办 | bizId 字段长度 64，超长截断或改用 hash 标识 — plan 阶段决定 |
